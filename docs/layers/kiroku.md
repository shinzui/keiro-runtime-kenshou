# Kiroku layer

The `kiroku` layer checks the PostgreSQL event store in an isolated, migrated database. Run a scenario from the repository root inside `nix develop`:

```bash
cabal run -v0 kenshou -- list --layer kiroku
cabal run -v0 kenshou -- run kiroku/append/correctness/expected-version-matrix --out runs/
```

The eighteen ordinary correctness scenarios are listed below. Global order, cursor semantics, partition coverage, catch-up handoff, idle category, and overflow policy use the `standard` tier; the other twelve use `smoke`. All have `either` placement and support PostgreSQL 17 and 18, and both `fsync-off` and `durable` modes. The separate batch-size validation known-defect scenario uses tier `standard`.

| Scenario | Contract checked |
| --- | --- |
| `kiroku/append/correctness/expected-version-matrix` | Append preconditions on missing, live and soft-deleted streams, plus invalid names and empty batches. |
| `kiroku/append/correctness/idempotent-event-ids` | Caller event IDs reject retry, cross-stream and larger-batch duplicates without changing versions or the global log. The optional parsed ID in `DuplicateEvent` may be absent. |
| `kiroku/append/correctness/multi-stream-atomicity` | Multi-stream appends commit all operations or none when a precondition, reserved stream name or empty batch fails. |
| `kiroku/append/correctness/all-order-and-gaps` | A 5,000-event, 50-stream workload mixing single and multi-stream appends preserves append and read order; native counts agree before hard deletes, and five deletes create exactly the reported gaps. The inventory head bounds the visible head. |
| `kiroku/read/correctness/cursor-semantics` | Paged global, stream, category and Streamly reads preserve order and exact membership; source stream names resolve from surrogate IDs. |
| `kiroku/lifecycle/correctness/delete-and-truncate` | Soft delete, restoration, truncation, reserved stream protection, hard delete, its event handler signal and a live `$all` subscriber that stays ordered throughout. |
| `kiroku/transaction/correctness/append-with-continuation` | Caller SQL and an event append commit together; a condemned transaction rolls both back; a rejected version skips the continuation. The basic wrapper bypasses an enrichment hook while the resource-aware wrapper applies it. |
| `kiroku/subscription/correctness/checkpoint-policies` | Missing checkpoints refuse startup or initialize at zero or the current head; existing rows win; explicit reset reports missing names and causes redelivery. |
| `kiroku/subscription/correctness/catchup-live-handoff` | A 5,000-event prepopulation and paced appender run through twenty graceful restarts; native all-stream and category subscribers preserve coverage, order and monotonic checkpoints. The plain and acknowledgement coupled Streamly bridges also consume catch-up history and a subsequent live append in order. |
| `kiroku/subscription/correctness/category-idle-no-spin` | During a 90-second steady phase at about 500 unrelated events per second, an idle category subscription issues at most `floor(seconds / 30) + 2` live fetches; the consumer-group fetch count is recorded separately. |
| `kiroku/subscription/correctness/overflow-policies` | A one-batch queue under 3,000 single-event appends exercises pause and resume without loss, typed overflow with successful restart, and lossy oldest-batch dropping while the worker stays alive. |
| `kiroku/subscription/correctness/filters-advance-checkpoint` | The event type filter and selector compose; 2,000 skipped events still advance the durable checkpoint to the global head. |
| `kiroku/dead-letter/correctness/retry-and-dead-letter` | A retrying event is delivered exactly the configured number of times and persisted once with the exhaustion reason; explicit poison is persisted once; the checkpoint reaches the head. |
| `kiroku/notifier/correctness/wake-latency` | All-stream, category and consumer-group subscribers enter live mode, receive 200 paced appends in order, and deliver each within five seconds of append start. |
| `kiroku/retention/correctness/leases-block-hard-delete` | An active lease blocks API hard deletion and raw SQL with SQLSTATE `KR001`; owner mismatch rejects renewal, release and passive expiry permit deletion, and duration bounds are enforced. |
| `kiroku/metrics/correctness/endpoints-truthful` | JSON and Prometheus report the known global head; live and ready health respond truthfully, a held subscriber makes readiness fail, and a WebSocket tail replays then delivers live events once and in order. The collector reports zero lag after caught-up workers stop gracefully. |
| `kiroku/otel/correctness/spans-and-trace-context` | In-memory spans show catch-up, delivery batch size and an error-ended retry episode; a producer span's trace identifier survives append and subscription delivery. The `collect` arm checks composed metrics and tracing handlers. |
| `kiroku/consumer-group/correctness/partition-coverage` | 500 streams and 10,000 events are delivered exactly once across members, each stream matches PostgreSQL's hash slot and stays in order, checkpoint rows cover every member, and invalid group definitions are rejected. |

All eighteen accept `kiroku.pool-size` (1 to 64, default 10), `kiroku.statement-timeout-seconds` (0 to 600, default 0, where zero disables the timeout), `kiroku.idle-in-transaction-timeout-seconds` (1 to 3600, default 30), and `kiroku.conn.keepalives` (boolean, default false). The read scenario also accepts `kiroku.read.page-size` (1 to 1000, default 256; declared variants 1, 7, 256, 1000). The global-order scenario accepts `workload.events` (100 to 100,000, default 5,000) and `kiroku.append.streams` (5 to 1,000, default 50). The dead-letter scenario accepts `kiroku.subscription.retry-max-attempts` (1 to 10, default 3, variants 1 and 3). The retention scenario accepts `kiroku.retention.lease-seconds` (1 to 3600, default 5, variants 1 and 5). The consumer-group scenario accepts `kiroku.consumer-group.size` (1, 2, 3, 4 or 8; default 4) and `kiroku.subscription.target` (`all` or `category`; default `all`). The handoff scenario accepts `kiroku.subscription.target`, `kiroku.subscription.batch-size` (1 to 10,000, default 100), `handoff.rounds` (1 to 100, default 20) and `workload.prepopulate` (1 to 100,000, default 5,000). The overflow scenario accepts `kiroku.subscription.overflow-policy` (`pause-and-resume`, `drop-subscription` or `drop-oldest`), `kiroku.subscription.queue-capacity` (1 to 1024, default 1) and `kiroku.subscription.handler-latency-ms` (1 to 1000, default 20). The idle category scenario has a 90-second steady phase, which can be shortened locally with `--phase steady=5`. Metrics endpoints support `telemetry.metrics=serve` and `serve-scraped`. The OTel scenario requires `telemetry.tracing=sdk-inmemory` and supports metrics `off` or `collect`; the other scenarios restrict telemetry arms to `off`.

The change-aware planner should map `kiroku/append/**` and the other store components to `kiroku-store` and `kiroku-store-migrations`, `kiroku/metrics/**` to `kiroku-metrics`, and `kiroku/otel/**` to `kiroku-otel`. The metrics and OTel components include both correctness and benchmark scenarios; OTel also includes the slow-handler concurrency scenario.

The benchmark scenarios use tier `standard` and placement `either`. The concurrency scenarios also use tier `standard`; `postgres-restart`, `network-partition`, `listen-kill-and-notify-loss`, and `all-lock-hold` require placement `local`, while the others use `either`. The three reduced soak names are `kiroku/subscription/soak/append-and-subscribe-reduced`, `kiroku/dead-letter/soak/dead-letter-growth-reduced`, and `kiroku/retention/soak/lease-churn-reduced`; each uses tier `extended` and placement `either`. Their unsuffixed counterparts use tier `soak` and placement `cell`. `kenshou list --layer kiroku --json` emits the tiers, placements, and known-defect references for all 53 scenarios; the knob ranges and notable variants are described with each workload below.

All Kiroku scenarios accept the four store knobs listed above. Benchmarks and soaks also accept the shared load knobs: `load.model` (`closed`, `open-constant`, `open-poisson`), `load.workers` (1–65,535), `load.think-time-us` (0–60,000,000), `load.rate-per-second` (0.001–10,000,000), `load.executors` (1–65,535), `load.max-lag-ms` and `load.abort-lag-ms` (each 1–3,600,000). Their shared measurement knobs are `measure.sample-interval-ms` (100–60,000), `measure.raw-samples` (`full`, `sampled`, `off`), `measure.raw-sample-one-in` (1–1,000,000), `measure.histogram-digits` (1–5), `measure.interval-histogram-seconds` (1–86,400), and `measure.pg-statements` (`off`, `snapshots`, `periodic`). The benchmark default is closed-loop with full raw samples unless a scenario states otherwise. Soaks default to open-constant at 200 operations per second and retain one raw sample in 100; their workload-specific knobs are listed in Soak coverage.

Every named correctness and concurrency verdict cell is classified `contract` unless specified here as `implementation`: `all-order-and-gaps` labels `before-gapless` and `after-gaps-match-deletes`; `idempotent-event-ids` labels `all-position-unchanged`; `category-idle-no-spin` labels `idle-category-fetch-bound`; `catchup-live-handoff` labels `no-duplicates-inside-incarnation` and `graceful-restart-duplicate-budget`; `all-order-under-contention` labels `global-positions-contiguous` and `durable-three-counts-agree`; `multi-process-members` labels `duplicate-budget-per-member`; `sigkill-redelivery-window` labels `per-crash-duplicate-budget`; and `all-lock-hold` labels `plain-appenders-blocked-by-holder`. The five known-defect scenarios and their canonical upstream references are listed below. Benchmarks and soaks report measurements and resource verdicts rather than contractual verdict cells.

`network-partition` also carries the reconnect defect reference because its category path can replay history. Its observed 60-second recovery miss is a separate blocking failure, so that run reports `different-failure` rather than a nonblocking known defect.

The shared SQL oracle reads the migrated `kiroku` tables through a separate pool query, pages the `$all` log by stream version, and reports gaps against its durable head. It also audits stream versions and reads the frozen checkpoint view, dead letters, partition slots and PostgreSQL deadlock counter. The append, dead-letter, consumer-group and process-race scenarios exercise those queries against the API observations.

## Benchmarks

`kiroku/append/benchmark/append-only` runs one stream per writer with `AnyVersion`; `kiroku/append/benchmark/hot-stream` uses one shared stream. Both record append latency, event throughput, errors, raw samples, histograms and PostgreSQL time series. Their default phases are 30 seconds warm-up, 120 seconds steady and 15 seconds drain. Set `kiroku.append.writers` (1 to 128, default 32), `kiroku.append.batch-size` (1 to 100, default 1), `kiroku.append.payload-bytes` (64 to 65,536, default 256), and the shared `kiroku.pool-size`. The measurement toolkit accepts `load.model=closed|open-constant|open-poisson`, `load.rate-per-second` for open loop, and its `measure.*` sampling knobs. The scenario uses `kiroku.append.writers` for closed-loop workers; `load.workers` is declared by the shared toolkit but does not override that scenario knob.

Every benchmark summary includes a `methodology` object. A local run is exploratory; on macOS `fsync` alone does not establish a drive-cache flush unless `wal_sync_method=fsync_writethrough`. The benchmark reads that PostgreSQL setting and records the reason when it is unsuitable. PostgreSQL checkpoints inside a steady window are visible in the measurement health report. Compare at least three paired and interleaved trials before quoting a difference; a single laptop trial is a smoke check, not a performance claim. The expected pool optimum of 8 to 13 connections and a throughput loss of at least 20 percent at 32 connections is a hypothesis for a controlled cell run, not an assertion in the benchmark.

`kiroku/read/benchmark/read-targets` prepopulates 100,000 events by default across 16 streams in 8 categories before warm-up. It records per-page read latency and event throughput for single-stream, `$all`, and category targets. Forward and backward paged reads are available where the released store has those APIs; its Streamly read API exists only for single-stream forward reads, and category reads have no backward API. Unsupported combinations return a named failure. Reduced PostgreSQL 18 durable runs passed for paged single forward, Streamly single forward, paged category forward, and paged `$all` backward. Short local runs at 500 reads per second were paced to stay under the measurement driver's CPU threshold and provide enough samples; these are exploratory checks, not performance comparisons.

`kiroku/subscription/benchmark/catch-up` prepopulates 100,000 events by default before warm-up, then repeatedly creates fresh named subscriptions and times each through `KirokuEventSubscriptionCaughtUp`. It checks that handlers saw every prepopulated event. Knobs: `workload.prepopulate` (100 to 1,000,000), `kiroku.subscription.batch-size` (1 to 1,000, default 100), `kiroku.subscription.target` (`all` or `category`), and `kiroku.consumer-group.size` (0 for non-group, 1 to 8 for grouped). The benchmark uses one closed-loop operation worker so each measurement is a separate cold catch-up; its default phases are 30/120/15 seconds. A full PostgreSQL 18 durable run completed 140 100,000-event catches with zero failures, including 110 steady samples. Reduced `$all` and category size-three group runs also had zero operation failures. Local grades were inconclusive due measurement health limits, not catch-up correctness failures.

`kiroku/subscription/benchmark/append-to-handler-latency` runs an appender worker and a subscriber worker in separate processes, joins their acknowledgement and handler-entry timestamps by caller event ID, and records raw `append-to-handler` samples. Both processes run on one host, so the monotonic clock has a zero cross-host skew bound; handler entries that precede the acknowledgement are counted and clamped to zero for the unsigned histogram. `kiroku.append.writers` defaults to 8, `kiroku.subscription.target` supports `$all` and category, and the default load is open-constant at 500 appends per second. Paced 100/s PostgreSQL 18 durable `$all` and category runs each matched all 1,233 acknowledgements, passed measurement health and agreed with three durable counts; local p99 was about 0.41 and 0.53 ms. A full default 30/120/15-second PostgreSQL 18 durable `$all` run matched all 75,036 acknowledgements, had zero load failures, agreed with all three durable counts, and earned benchmark-grade measurement health. Its local p99 was about 0.47 ms; the methodology summary marks it non-authoritative because it ran on macOS with `wal_sync_method=open_datasync`.

`kiroku/subscription/benchmark/fan-out` starts 1 to 64 named subscribers over 1 to 16 worker processes. Subscribers in one process share a store and publisher. It appends to eight streams at 500 events per second by default, checks every subscriber's delivery count and contiguous global positions against the durable event count, and records sampled append-start-to-handler-entry latencies. `kiroku.subscription.subscribers` defaults to 4, `kiroku.subscription.processes` to 1, and `kiroku.subscription.sample-every` to 20. `$all` and category targets are supported. A short PostgreSQL 18 durable category trial with four subscribers across two processes delivered all 6,038 events to each subscriber with no order violations, matched the expected 1,204 sampled deliveries, and passed measurement health; local p99 was about 6 ms. The full default 30/120/15-second `$all` run delivered all 75,037 events in order to each of four subscribers, captured all 15,004 expected samples, and earned benchmark-grade measurement health; local p99 was about 4 ms. Short 16- and 64-subscriber variants passed with 6,036 and 1,233 events per subscriber respectively; a short one-subscriber variant also delivered all 6,036 but was measurement-inconclusive because it yielded only 301 steady samples. These local numbers are non-authoritative under the durability methodology above.

`kiroku/otel/benchmark/event-handler-arms` appends to one stream per writer while four `$all` subscribers consume every event. The `telemetry.tracing` arms are `off`, `noop`, `sdk-inmemory`, and `sdk-otlp`; `telemetry.metrics` supports `off` and `collect`. `off`/`off` leaves Kiroku's event handler absent. `kiroku.trace.enrich-event=true` creates a producer span and injects its trace context into each event before append. The run checks the four subscriber counts against all three durable counts. If a drain cancels an append after commit but before its operation returns, the run reports an ambiguous completion as inconclusive. Short paced PostgreSQL 18 durable baseline, no-op plus collect, and in-memory plus collect with enrichment arms passed. These local runs are measurement-grade but non-authoritative under the methodology above.

A three-pair `kenshou overhead` comparison of off versus no-op tracing at 100 appends/s produced a passing `kenshou.overhead-report/v1` in `runs/overhead-01a0ccbc-a975-7442-a164-da1578ea0c2a/overhead-report.json`. Its local relative p99 latency delta was about -0.41%, throughput was effectively flat, and allocation per operation rose about 2.15%. The confidence intervals for latency and throughput included zero; this is local, non-authoritative evidence.

`kiroku/metrics/benchmark/server-arms` uses the same append and four-subscriber workload. `telemetry.metrics=collect` keeps collection in process, `serve` starts Kiroku's HTTP and WebSocket server, and `serve-scraped` additionally registers the JSON and Prometheus endpoints with the telemetry scraper. Set `metrics.scrape-interval-ms` to 15000 or 1000 for the requested scrape cells. `kiroku.metrics.websocket-tails` accepts 0, 1, or 8; the scenario verifies that each requested tail connects and receives events. Short PostgreSQL 18 durable collect, serve with eight tails, and serve-scraped with one-second scrapes and one tail runs passed. The scraped run observed 12 successful scrapes of each Kiroku endpoint with no failures.

`kiroku/otel/concurrency/slow-event-handler-stalls-delivery` prepopulates 20,000 events and adds a configurable 50 ms delay to Kiroku's subscription-delivered callback. It compares delivery during a two-second delayed window with the first second after removing the delay, then verifies complete delivery and the final checkpoint. The default PostgreSQL 18 durable run passed all six cells. `kiroku.handler.delay-ms` and `kiroku.handler.events` control the delay and prepopulation size.

## Soak coverage

Each soak has a full `soak`-tier form with a four-hour steady phase and an `extended`-tier `-reduced` form with a 30-minute steady phase. Both use durable PostgreSQL 17 or 18. `soak.duration-minutes` changes the steady duration; `soak.kill-interval-minutes` defaults to 10 and accepts 0 to disable kills; `soak.verify-interval-minutes` defaults to 30. The default open-loop load is 200 operations per second. A short run can confirm the delivery contract but reports `inconclusive` for resource growth until the leak judge has enough samples. The append-and-subscribe pair also supports `--dim telemetry.tracing=sdk-otlp` to exercise tracing from its parent-process subscribers during the leak window.

| Scenario pair | Checks |
| --- | --- |
| `kiroku/subscription/soak/append-and-subscribe` | Appends over 1,000 streams in eight categories while two native `$all`, two category, a three-member process group, and an ack-stream subscriber consume. Group members are killed and restarted. Durable counts, local order, category counts, group coverage, checkpoint progress, and a duplicate budget are checked. |
| `kiroku/dead-letter/soak/dead-letter-growth` | Marks one percent of appends as poison, retries them to exhaustion in a separate subscriber process, kills and restarts that process, then matches each poison global position to exactly one dead letter. |
| `kiroku/retention/soak/lease-churn` | Acquires, renews, releases, expires, and prunes retention leases while attempting hard deletes. Active leases must block deletion; final pruning must leave no lease rows. A progress watchdog captures a 60-second operation stall, and the final PostgreSQL deadlock count must match the starting count. A short PostgreSQL 18 trial completed 453 operations with zero deadlocks and no remaining leases; the resource verdict was inconclusive because its observation window was short. |

Short PostgreSQL 18 durable trials passed the workload checks for all three pairs. The append-and-subscribe trial covered 2,133 positions with no group duplicates, and a three-minute trial covered 36,234 positions through three subscriber kills with zero duplicates and failures. The final full 30-minute reduced run in `runs/01a0cd3e-900b-7662-9803-74ea0fc723c3` passed with 372,034 durable events and three real subscriber kills. All subscriber and group coverage checks passed with zero group duplicates; p99 drift stayed within factor two, event-table growth was linear, the eight subscription rows stayed constant, and HOT updates reached 99.9997%. Every bounded leak probe was `stable`; fifteen post-major heap samples showed 569,200 bytes of growth, while descriptors stayed flat after the restarts. The earlier full trial's heap failure was a false positive from samples taken without a major GC. The dead-letter trial matched 22 poison events to 22 dead letters; a 70-second trial survived one subscriber kill and matched all 36 poison events to 36 dead letters. Each short trial was `inconclusive` overall because its leak observation window was too short. A short `sdk-otlp` append trial covered all 2,133 events and exported 7,636 spans with no drops or export failures.

`kiroku/transaction/benchmark/lock-hold-contention` mixes plain appends and `runTransactionAppending` at a configurable fraction (default 0.2). Its continuation executes 0 to 20 probe inserts while the append transaction holds the `$all` row lock. Separate latency histograms for plain, transaction and whole-attempt operations expose the cost to unrelated appenders. A paced 25-second PostgreSQL 18 durable run with one continuation statement passed with 4,860 plain and 1,391 transaction samples; the local methodology labels it exploratory. Compare paired continuation-statement cells on the same controlled host before drawing a performance conclusion.

`kiroku/append/benchmark/layer-ladder` measures four rungs: a raw bytea insert, a PL/pgSQL function wrapping that insert, kiroku's prepared `appendAnyVersion` statement called directly through Hasql, and the public `appendToStream` API. It creates the `kenshou_kiroku` table and function in the isolated database. The lock-free rungs use writers plus four connections by default; the two kiroku append rungs use ten. `kiroku.ladder.pool-size=0` applies that rung rule, while a positive value overrides it. All four reduced PostgreSQL 18 durable paced runs passed and wrote append histograms; these local runs do not establish a throughput ratio.

The first local pool-size comparison used three interleaved pool-10 and pool-32 pairs under 250 open-loop appends per second and the policy in `docs/policies/kiroku-local-pool-comparison.json`. `kenshou compare` returned `inconclusive`: throughput passed at the imposed rate, while the p99 latency confidence interval crossed the policy limit. The macOS runs remain non-authoritative for the pool optimum hypothesis.

`kiroku/append/benchmark/expected-version-conflict` precreates its hot stream. Each closed-loop writer attempts an `ExactVersion` append, rereads the actual stream version after a conflict, and retries in its next operation. It records separate `append-ok`, `append-conflict`, `reread`, and whole-attempt histograms. At least one append and conflict must occur, and the durable version must equal one seed event plus successful batch appends. A short local run with four writers recorded 1,751 winning appends, 5,225 conflicts, no unexpected errors, and final version 1,752. The benchmark uses the same writer, batch, payload, pool and measurement knobs as the other append benchmarks and requires closed-loop load.

## Concurrency coverage

| Scenario | Contract checked |
| --- | --- |
| `kiroku/append/concurrency/expected-version-race` | Two or four worker processes race 8 to 32 writers over 1 to 16 precreated streams. Exactly one writer wins each expected version, all other writers report a version conflict, and a durable stream read has versions 1 through the final head. The default steady phase is 60 seconds and requires durable PostgreSQL. |
| `kiroku/append/concurrency/idempotent-duplicates` | Four processes submit identical caller-ID batches behind each request round, first with `AnyVersion`, then `ExactVersion`. One append wins each of 500 default batches, each identifier occurs once, and the final version is 5,000. Both PostgreSQL versions passed; PostgreSQL 18 recorded 750 duplicate errors and 750 wrong-version errors. |
| `kiroku/append/concurrency/model-based-occ` | Two or three concurrent calls per case exercise exact and any-version appends, stream reads, get, soft delete and undelete across six seeded streams. A pure stream model and the shared linearizability checker test every ordering consistent with observed call times. On failure the scenario reruns smaller branch sets in fresh streams and records the reduced history and seed in a replay verdict. The earlier default 200 cases passed on PostgreSQL 17 and 18, with 146 expected version conflicts on PostgreSQL 18; a 20-case PostgreSQL 18 durable run passed after the six-stream and shared-checker changes. A unit test rejects an intentionally mutated result. Knobs: `model.cases` (1 to 1,000, default 200) and `model.branches` (2 to 3, default 3). |
| `kiroku/append/concurrency/sigkill-mid-append` | A child appender receives 100 caller-ID events per batch, is killed at seeded instants, restarted and sent the same batch. The state immediately after each kill is all-or-none; after retry every batch has its exact IDs and version, and PostgreSQL's three durable counts agree. Ten default kills passed on PostgreSQL 17 and 18 with one retry committing a previously absent batch and nine recognizing already committed batches. Knobs: `crash.kills` (1 to 100, default 10) and `kiroku.append.batch-size` (1 to 1,000, default 100). |
| `kiroku/append/concurrency/all-order-under-contention` | Two appender processes run 32 writers on separate streams with batches of 1 to 20 events. A separate reader process tails `$all` while a native `$all` subscriber receives the same writes. Both observed sequences must equal the final durable global read; acknowledged positions rise within each writer, stream versions and global positions are contiguous, and PostgreSQL's three durable counts agree. The default 120-second PostgreSQL 18 durable run passed all eight cells across 1,275,200 events. Knobs: `kiroku.append.writers` (2 to 32, default 32), `kiroku.append.processes` (2 to 4, default 2), and `workload.round-events` (32 to 1,000, default 100). |
| `kiroku/consumer-group/concurrency/duplicate-member-claim` | Two separate processes claim member 0 of a size-2 group, with member 1 active in a third process. After a two-second stagger, 200 events are appended. The union of deliveries must cover all events, each process's positions and sampled member checkpoints must be monotonic, and the final checkpoint rows must exist. On PostgreSQL 18 with the startup guard off and on, both runs passed six cells; the two member-0 processes each observed 114 common positions, documenting overlapping ownership. The `kiroku.consumer-group.guard` knob defaults to false and supports true. |
| `kiroku/consumer-group/concurrency/multi-process-members` | Four separate process members consume a size-4 group over 100 streams. Eight seeded SIGKILLs restart members 0, 3, 2 and 1 twice each while appends continue. The worker emits each handler delivery to the supervisor before acknowledgement, retaining evidence across a crash. The default PostgreSQL 18 durable run passed all five cells: exactly 1,000 positions were covered, all SQL hash slots agreed, each incarnation stayed ordered, checkpoints rose monotonically, and the per-crash duplicate budget held. Knobs: `kiroku.consumer-group.size` (2 to 8, default 4) and `crash.kills` (1 to 32, default 8). |
| `kiroku/subscription/concurrency/sigkill-redelivery-window` | A subscriber receives batches of 500 events and is interrupted after about 150 handler entries, then restarted under the same name. The default ten-kill native PostgreSQL 18 durable runs passed all five cells for `$all` and category targets: all 5,000 positions arrived, each incarnation stayed ordered, checkpoints rose, and duplicates remained in the interrupted batches. `$all` redelivered 150 to 151 positions per kill, within the publisher's 1,000-event budget; category redelivered 50 to 51, within its configured 100-event batch budget. One-kill PostgreSQL 18 durable trials passed for both Streamly APIs under SIGKILL, for the acknowledged API under SIGTERM and graceful cancellation, and for native and acknowledged APIs under an injected handler exception. Knobs: `crash.kills` (1 to 32, default 10), `kiroku.subscription.batch-size` (1 to 1,000, default 100), `kiroku.subscription.target` (`all` or `category`), `kiroku.subscription.api` (`native`, `plain`, or `ack`), and `crash.mode` (`sigkill`, `sigterm`, `cancel`, or `handler-exception`). |
| `kiroku/subscription/concurrency/postgres-restart` | Under 100 ten-event caller-ID appends, the local PostgreSQL postmaster is restarted once fast and once with an immediate stop. Appends retry with stable identifiers. The oracle checks durable IDs and counts, complete ordered subscriber delivery, monotonic checkpoint samples, duplicates within two publisher batches, and the first delivery within 90 seconds of the immediate restart. The PostgreSQL 18 durable run delivered all 1,000 events with zero duplicates and 29 retry errors; first delivery took 89.38 seconds. |
| `kiroku/notifier/concurrency/listen-kill-and-notify-loss` | Three process subscribers cover native `$all`, category, and a size-one consumer group while 900 events are appended over 180 seconds. Three 20-second listener backend kill cycles are followed by 70 seconds with both notification triggers disabled. The PostgreSQL 18 durable run killed four listener backends per cycle and observed three reconnects; each path delivered all 900 events in order, its checkpoint reached the head, and all 346 events appended during the outage arrived within 35 seconds. PostgreSQL reported both triggers disabled during the fault and restored afterward; the maximum observed delivery delay was about 1.02 seconds. |
| `kiroku/subscription/concurrency/network-partition` | Three process subscribers use the TCP fault proxy while a direct producer appends 320 events. The proxy resets existing connections, blackholes traffic for 20 seconds, resets again, then adds 50 ms latency. `kiroku.conn.keepalives` defaults to true here and supports false. The PostgreSQL 18 durable run reported a blocking recovery miss: native `$all` and group paths stayed at 100 at the 60-second deadline after the blackhole, while category reached 300. All three eventually delivered and checkpointed 320. Category replayed 100 positions after reconnect, linked to `mori://shinzui/kiroku/plans/82-repair-live-reconnect-and-validate-subscription-identity-and-batch-size`; the recovery miss is a separate failure. |
| `kiroku/transaction/concurrency/all-lock-hold` | A separate `kiroku/tx-appender` worker calls `runTransactionAppending` with a probe insert and `pg_sleep` in the continuation, then receives SIGKILL while holding the `$all` lock. Three plain appenders start during the hold. On PostgreSQL 18 durable at the default 200 ms hold, a plain appender was observed waiting on the transaction backend, none completed before the kill, the transaction's event and probe row rolled back, and the plain appends committed at positions 1–3 about 191 ms later. A 5-second hold also passed with a watchdog `lock-wait` diagnosis, then recovered the three plain appends. Knob: `kiroku.tx.continuation-sleep-ms` (100 to 5,000, default 200). |

| `kiroku/subscription/correctness/batch-size-validation` | Batch sizes 0 and -1 should be refused within five seconds without handler calls.
