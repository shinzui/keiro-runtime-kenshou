# Kiroku layer

The `kiroku` layer checks the PostgreSQL event store in an isolated, migrated database. Run a scenario from the repository root inside `nix develop`:

```bash
cabal run -v0 kenshou -- list --layer kiroku
cabal run -v0 kenshou -- run kiroku/append/correctness/expected-version-matrix --out runs/
```

The implemented scenarios are listed below. The global-order and cursor scenarios use the `standard` tier; the rest use `smoke`. They all have `either` placement and support PostgreSQL 17 and 18, and both `fsync-off` and `durable` PostgreSQL modes. Each writes a separate `kenshou.verdict/v1` verdict for every assertion into the run's `verdicts/` directory. The verdict marks a documented guarantee as `contract` and an incidental behavior as `implementation`.

| Scenario | Contract checked |
| --- | --- |
| `kiroku/append/correctness/expected-version-matrix` | Append preconditions on missing, live and soft-deleted streams, plus invalid names and empty batches. |
| `kiroku/append/correctness/idempotent-event-ids` | Caller event IDs reject retry, cross-stream and larger-batch duplicates without changing versions or the global log. The optional parsed ID in `DuplicateEvent` may be absent. |
| `kiroku/append/correctness/multi-stream-atomicity` | Multi-stream appends commit all operations or none when a precondition, reserved stream name or empty batch fails. |
| `kiroku/append/correctness/all-order-and-gaps` | A 5,000-event, 50-stream workload mixing single and multi-stream appends preserves append and read order; native counts agree before hard deletes, and five deletes create exactly the reported gaps. The inventory head bounds the visible head. |
| `kiroku/read/correctness/cursor-semantics` | Paged global, stream, category and Streamly reads preserve order and exact membership; source stream names resolve from surrogate IDs. |
| `kiroku/lifecycle/correctness/delete-and-truncate` | Soft delete, restoration, truncation, reserved stream protection, hard delete, its event handler signal and a live `$all` subscriber that stays ordered throughout. |
| `kiroku/transaction/correctness/append-with-continuation` | Caller SQL and an event append commit together; a condemned transaction rolls both back; a rejected version skips the continuation. The basic wrapper bypasses an enrichment hook while the resource-aware wrapper applies it. |
| `kiroku/subscription/correctness/checkpoint-policies` | Missing checkpoints refuse startup or initialize at zero or the current head; existing rows win; explicit reset reports missing names and causes redelivery. |
| `kiroku/subscription/correctness/catchup-live-handoff` | A 5,000-event prepopulation and paced appender run through twenty graceful restarts; native all-stream and category subscribers preserve coverage, order and monotonic checkpoints. The plain and acknowledgement coupled Streamly bridges also consume catch-up history and a subsequent live append in order. |
| `kiroku/subscription/correctness/category-idle-no-spin` | During a 90-second steady phase at about 500 unrelated events per second, an idle category subscription issues at most `floor(seconds / 30) + 2` live fetches; the consumer-group fetch count is recorded separately. |
| `kiroku/subscription/correctness/overflow-policies` | A one-batch queue under 3,000 single-event appends exercises pause and resume without loss, typed overflow with successful restart, and lossy oldest-batch dropping while the worker stays alive. |
| `kiroku/subscription/correctness/filters-advance-checkpoint` | The event type filter and selector compose; 2,000 skipped events still advance the durable checkpoint to the global head. |
| `kiroku/dead-letter/correctness/retry-and-dead-letter` | A retrying event is delivered exactly the configured number of times and persisted once with the exhaustion reason; explicit poison is persisted once; the checkpoint reaches the head. |
| `kiroku/notifier/correctness/wake-latency` | All-stream, category and consumer-group subscribers enter live mode, receive 200 paced appends in order, and deliver each within five seconds of append start. |
| `kiroku/retention/correctness/leases-block-hard-delete` | An active lease blocks API hard deletion and raw SQL with SQLSTATE `KR001`; owner mismatch rejects renewal, release and passive expiry permit deletion, and duration bounds are enforced. |
| `kiroku/metrics/correctness/endpoints-truthful` | JSON and Prometheus report the known global head; live and ready health respond truthfully, a held subscriber makes readiness fail, and a WebSocket tail replays then delivers live events once and in order. The collector reports zero lag after caught-up workers stop gracefully. |
| `kiroku/otel/correctness/spans-and-trace-context` | In-memory spans show catch-up, delivery batch size and an error-ended retry episode; a producer span's trace identifier survives append and subscription delivery. The `collect` arm checks composed metrics and tracing handlers. |
| `kiroku/consumer-group/correctness/partition-coverage` | 500 streams and 10,000 events are delivered exactly once across members, each stream matches PostgreSQL's hash slot and stays in order, checkpoint rows cover every member, and invalid group definitions are rejected. |

All eighteen accept `kiroku.pool-size` (1 to 64, default 10), `kiroku.statement-timeout-seconds` (0 to 600, default 0, where zero disables the timeout), `kiroku.idle-in-transaction-timeout-seconds` (1 to 3600, default 30), and `kiroku.conn.keepalives` (boolean, default false). The read scenario also accepts `kiroku.read.page-size` (1 to 1000, default 256; declared variants 1, 7, 256, 1000). The global-order scenario accepts `workload.events` (100 to 100,000, default 5,000) and `kiroku.append.streams` (5 to 1,000, default 50). The dead-letter scenario accepts `kiroku.subscription.retry-max-attempts` (1 to 10, default 3, variants 1 and 3). The retention scenario accepts `kiroku.retention.lease-seconds` (1 to 3600, default 5, variants 1 and 5). The consumer-group scenario accepts `kiroku.consumer-group.size` (1, 2, 3, 4 or 8; default 4) and `kiroku.subscription.target` (`all` or `category`; default `all`). The handoff scenario accepts `kiroku.subscription.target`, `kiroku.subscription.batch-size` (1 to 10,000, default 100), `handoff.rounds` (1 to 100, default 20) and `workload.prepopulate` (1 to 100,000, default 5,000). The overflow scenario accepts `kiroku.subscription.overflow-policy` (`pause-and-resume`, `drop-subscription` or `drop-oldest`), `kiroku.subscription.queue-capacity` (1 to 1024, default 1) and `kiroku.subscription.handler-latency-ms` (1 to 1000, default 20). The idle category scenario has a 90-second steady phase, which can be shortened locally with `--phase steady=5`. Metrics endpoints support `telemetry.metrics=serve` and `serve-scraped`. The OTel scenario requires `telemetry.tracing=sdk-inmemory` and supports metrics `off` or `collect`; the other scenarios restrict telemetry arms to `off`.

The change-aware planner should map `kiroku/append/**` and the other store components to `kiroku-store` and `kiroku-store-migrations`, `kiroku/metrics/**` to `kiroku-metrics`, and `kiroku/otel/**` to `kiroku-otel`. Both component families have correctness scenarios; their benchmark and concurrency scenarios remain planned.

The shared SQL oracle reads the migrated `kiroku` tables through a separate pool query, pages the `$all` log by stream version, and reports gaps against its durable head. It also audits stream versions and reads the frozen checkpoint view, dead letters, partition slots and PostgreSQL deadlock counter. The append, dead-letter, consumer-group and process-race scenarios exercise those queries against the API observations.

## Benchmarks

`kiroku/append/benchmark/append-only` runs one stream per writer with `AnyVersion`; `kiroku/append/benchmark/hot-stream` uses one shared stream. Both record append latency, event throughput, errors, raw samples, histograms and PostgreSQL time series. Their default phases are 30 seconds warm-up, 120 seconds steady and 15 seconds drain. Set `kiroku.append.writers` (1 to 128, default 32), `kiroku.append.batch-size` (1 to 100, default 1), `kiroku.append.payload-bytes` (64 to 65,536, default 256), and the shared `kiroku.pool-size`. The measurement toolkit accepts `load.model=closed|open-constant|open-poisson`, `load.rate-per-second` for open loop, and its `measure.*` sampling knobs. The scenario uses `kiroku.append.writers` for closed-loop workers; `load.workers` is declared by the shared toolkit but does not override that scenario knob.

Every benchmark summary includes a `methodology` object. A local run is exploratory; on macOS `fsync` alone does not establish a drive-cache flush unless `wal_sync_method=fsync_writethrough`. The benchmark reads that PostgreSQL setting and records the reason when it is unsuitable. PostgreSQL checkpoints inside a steady window are visible in the measurement health report. Compare at least three paired and interleaved trials before quoting a difference; a single laptop trial is a smoke check, not a performance claim. The expected pool optimum of 8 to 13 connections and a throughput loss of at least 20 percent at 32 connections is a hypothesis for a controlled cell run, not an assertion in the benchmark.

`kiroku/read/benchmark/read-targets` prepopulates 100,000 events by default across 16 streams in 8 categories before warm-up. It records per-page read latency and event throughput for single-stream, `$all`, and category targets. Forward and backward paged reads are available where the released store has those APIs; its Streamly read API exists only for single-stream forward reads, and category reads have no backward API. Unsupported combinations return a named failure. Reduced PostgreSQL 18 durable runs passed for paged single forward, Streamly single forward, paged category forward, and paged `$all` backward. Short local runs at 500 reads per second were paced to stay under the measurement driver's CPU threshold and provide enough samples; these are exploratory checks, not performance comparisons.

`kiroku/transaction/benchmark/lock-hold-contention` mixes plain appends and `runTransactionAppending` at a configurable fraction (default 0.2). Its continuation executes 0 to 20 probe inserts while the append transaction holds the `$all` row lock. Separate latency histograms for plain, transaction and whole-attempt operations expose the cost to unrelated appenders. A paced 25-second PostgreSQL 18 durable run with one continuation statement passed with 4,860 plain and 1,391 transaction samples; the local methodology labels it exploratory. Compare paired continuation-statement cells on the same controlled host before drawing a performance conclusion.

`kiroku/append/benchmark/expected-version-conflict` precreates its hot stream. Each closed-loop writer attempts an `ExactVersion` append, rereads the actual stream version after a conflict, and retries in its next operation. It records separate `append-ok`, `append-conflict`, `reread`, and whole-attempt histograms. At least one append and conflict must occur, and the durable version must equal one seed event plus successful batch appends. A short local run with four writers recorded 1,751 winning appends, 5,225 conflicts, no unexpected errors, and final version 1,752. The benchmark uses the same writer, batch, payload, pool and measurement knobs as the other append benchmarks and requires closed-loop load.

## Concurrency coverage

| Scenario | Contract checked |
| --- | --- |
| `kiroku/append/concurrency/expected-version-race` | Two or four worker processes race 8 to 32 writers over 1 to 16 precreated streams. Exactly one writer wins each expected version, all other writers report a version conflict, and a durable stream read has versions 1 through the final head. The default steady phase is 60 seconds and requires durable PostgreSQL. |
| `kiroku/append/concurrency/idempotent-duplicates` | Four processes submit identical caller-ID batches behind each request round, first with `AnyVersion`, then `ExactVersion`. One append wins each of 500 default batches, each identifier occurs once, and the final version is 5,000. Both PostgreSQL versions passed; PostgreSQL 18 recorded 750 duplicate errors and 750 wrong-version errors. |
| `kiroku/append/concurrency/model-based-occ` | Two or three concurrent calls per case exercise exact and any-version appends, stream reads, get, soft delete and undelete. A pure stream model checks every ordering consistent with observed call times. The default 200 cases passed on PostgreSQL 17 and 18, with 146 expected version conflicts on PostgreSQL 18. Knobs: `model.cases` (1 to 1,000, default 200) and `model.branches` (2 to 3, default 3). |
| `kiroku/append/concurrency/sigkill-mid-append` | A child appender receives 100 caller-ID events per batch, is killed at seeded instants, restarted and sent the same batch. The state immediately after each kill is all-or-none; after retry every batch has its exact IDs and version, and PostgreSQL's three durable counts agree. Ten default kills passed on PostgreSQL 17 and 18 with one retry committing a previously absent batch and nine recognizing already committed batches. Knobs: `crash.kills` (1 to 100, default 10) and `kiroku.append.batch-size` (1 to 1,000, default 100). |
| `kiroku/append/concurrency/all-order-under-contention` | Two appender processes run 32 writers on separate streams with batches of 1 to 20 events. A separate reader process tails `$all` while a native `$all` subscriber receives the same writes. Both observed sequences must equal the final durable global read; acknowledged positions rise within each writer, stream versions and global positions are contiguous, and PostgreSQL's three durable counts agree. The default 120-second PostgreSQL 18 durable run passed all eight cells across 1,275,200 events. Knobs: `kiroku.append.writers` (2 to 32, default 32), `kiroku.append.processes` (2 to 4, default 2), and `workload.round-events` (32 to 1,000, default 100). |
| `kiroku/consumer-group/concurrency/duplicate-member-claim` | Two separate processes claim member 0 of a size-2 group, with member 1 active in a third process. After a two-second stagger, 200 events are appended. The union of deliveries must cover all events, each process's positions and sampled member checkpoints must be monotonic, and the final checkpoint rows must exist. On PostgreSQL 18 with the startup guard off and on, both runs passed six cells; the two member-0 processes each observed 114 common positions, documenting overlapping ownership. The `kiroku.consumer-group.guard` knob defaults to false and supports true. |
| `kiroku/consumer-group/concurrency/multi-process-members` | Four separate process members consume a size-4 group over 100 streams. Eight seeded SIGKILLs restart members 0, 3, 2 and 1 twice each while appends continue. The worker emits each handler delivery to the supervisor before acknowledgement, retaining evidence across a crash. The default PostgreSQL 18 durable run passed all five cells: exactly 1,000 positions were covered, all SQL hash slots agreed, each incarnation stayed ordered, checkpoints rose monotonically, and the per-crash duplicate budget held. Knobs: `kiroku.consumer-group.size` (2 to 8, default 4) and `crash.kills` (1 to 32, default 8). |
| `kiroku/subscription/concurrency/sigkill-redelivery-window` | A native subscription receives batches of 500 events and is killed after about 150 handler entries, then restarted under the same name. The default ten-kill PostgreSQL 18 durable runs passed all five cells for `$all` and category targets: all 5,000 positions arrived, each incarnation stayed ordered, checkpoints rose, and duplicates remained in the interrupted batches. `$all` redelivered 150 to 151 positions per kill, within the publisher's 1,000-event budget; category redelivered 50 to 51, within its configured 100-event batch budget. Knobs: `crash.kills` (1 to 32, default 10), `kiroku.subscription.batch-size` (1 to 1,000, default 100), and `kiroku.subscription.target` (`all` or `category`). |

## Known defects

| Scenario | Desired contract and current observation |
| --- | --- |
| `kiroku/subscription/correctness/batch-size-validation` | Batch sizes 0 and -1 should be refused within five seconds without handler calls. Both were accepted on PostgreSQL 17 and 18 with the released cohort. This is a nonblocking known defect linked to `mori://shinzui/kiroku/plans/82-repair-live-reconnect-and-validate-subscription-identity-and-batch-size`. |
| `kiroku/consumer-group/concurrency/resize-leaves-gaps` | A group resized from two to three members should deliver all 200 events or refuse the topology change. The released cohort accepted the resize but delivered only 165 distinct events in the PostgreSQL 18 run. This is a nonblocking known defect linked to `mori://shinzui/kiroku/plans/81-make-consumer-group-topology-durable-and-resize-without-gaps`. |
| `kiroku/subscription/concurrency/decode-hook-stalls-subscribers` | A poison event causes the publisher decode hook to throw. Both live subscribers should progress past it or stop with an error. In a full 60-second PostgreSQL 18 run they remained at position 1 while three publisher loop errors were observed. This is a nonblocking known defect linked to `mori://shinzui/kiroku/plans/83-contain-persistent-publisher-decode-hook-failures`. |
| `kiroku/subscription/concurrency/reconnect-cursor-regression` | A live category subscriber receives 5,000 events, has its pooled PostgreSQL backends terminated, and then receives 100 more. All 5,100 positions remain covered and its durable checkpoint advances from 5,000 to 5,100, but all 5,000 initial events are delivered again; the allowed duplicate bound is one batch of 100. PostgreSQL 17 and 18 both reproduced this nonblocking defect, linked to `mori://shinzui/kiroku/plans/82-repair-live-reconnect-and-validate-subscription-identity-and-batch-size`. Knobs: `workload.live-events` (100 to 10,000, default 5,000), `workload.after-reconnect` (1 to 1,000, default 100), and `kiroku.subscription.batch-size` (1 to 1,000, default 100). |
| `kiroku/append/concurrency/multi-stream-fresh-deadlock` | Two worker processes race a fresh two-stream append against a single append to the second stream. The desired PostgreSQL deadlock count is unchanged. In 500 rounds with eight throttled CPU spinners, PostgreSQL 18 recorded 30 deadlocks and PostgreSQL 17 recorded 42; no partial multi-stream commit occurred and retrying the same caller IDs left durable rows unchanged. This is a nonblocking known defect linked to `mori://shinzui/kiroku/okf/improvement-requests/concepts/IR-7`. Knobs: `deadlock.rounds` (1 to 5,000, default 500) and `deadlock.spinners` (0 to 32, default 8). |
