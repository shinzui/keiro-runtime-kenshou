# Keiro runtime baseline report — 2026-09-29 checkpoint

**State: baseline in progress.** This is the technical triage report for the initial released-cohort pass of [MasterPlan 1](../masterplans/1-build-an-extensive-verification-suite-for-the-keiro-runtime.md). ## Baseline completion gates

The registry currently has ten completed plans and nine in progress; EP-15 has begun with wire contracts, a pure terminal-state oracle, order and fulfilment aggregates, a saga observation stream, a checked ledger seam, a pure effect-count precheck, a broker-lifecycle seam, and an acknowledgement-based outbox publisher bridge; it has no two-context run yet. Keiro's EP-13 is now the immediate coverage priority: its outbox, inbox, and queue matrices remain incomplete. The inbox default-rate reduced soak passed on a clean cell. The queue default-rate reduced soak passed every business check but needs a forced-major-GC heap control, while the outbox default-rate reduced soak passed its business and table checks but failed on an unattributed main-process thread diagnostic. All three full-duration soaks and the remaining non-soak matrices are open. EP-15 is the largest later attribution gap: isolated layer results do not yet establish two-context end-to-end behavior. EP-10 and EP-11 still need longer soaks, controlled benchmark and telemetry comparisons, and the remaining finding audits; EP-12 has a clean default-rate reduced soak, a repaired five-minute diagnostic replay, and a same-seed twenty-minute low-rate control, but still needs its full soak and the remaining matrix, while EP-14 still needs its planned matrices and soaks. EP-16 and EP-17 need the wider cell and remote-execution acceptance. EP-8's earlier local A/A controls were too noisy; the revised read/ack and invisible-backlog controls now pass on a leased cell, layer-ladder is inconclusive on p99, grouped-read awaits its revision-3 rerun, and the slow-handler sensitivity plus remaining noisy benchmark controls still need isolated confirmation. These PGMQ performance gates are deferred behind Keiro coverage. The old PGMQ read/ack controls timed a send inside every read/ack operation and cannot establish the planned preloaded-drain baseline. Scenario revision 3 corrects that workload; short local PostgreSQL 18 batch-archive and pop probes passed as smoke checks. The 48 existing findings are classified or explicitly under investigation; new runs can add findings that must be filed or disposed before the final report.

Before calling the initial baseline complete, each child plan must meet its own acceptance, each confirmed new observation must have an owner report or documented non-bug disposition, and the selected clean released-cohort run set must be recorded and attested in the historical bundle. Incomplete attestations remain visible and do not become confirmed evidence by editorial decision. The final report will name the exact immutable run set, compatible environment and cohort identity, per-scenario outcome, open owner issue, and any inconclusive comparison.

When owners provide fixes, use the change-aware plan to select affected scenarios, pin a new cohort, preserve this run set, and run matched scenarios with the same PostgreSQL major, workload, knobs, telemetry arm, seed policy, and controlled cell profile. Compare new measurements with interleaved paired trials and use `kenshou history --confirmed-only` for confirmed historical candidates. Record a new result and attestation for each rerun; never rewrite a baseline run or treat a passing focused upstream test as the whole-runtime comparison.
