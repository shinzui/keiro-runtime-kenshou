# Verify the assembled runtime end to end and under soak

This ExecPlan is a living document. The sections Progress, Surprises & Discoveries,
Decision Log, and Outcomes & Retrospective must be kept up to date as work proceeds.
If durable project context changes, update or create ADRs in docs/adr/ in the same change.


## Purpose / Big Picture

Every other coverage plan in this repository isolates one layer of the keiro runtime. This plan puts the layers back together the way a real service links them and asks the question no single layer can answer: when commands, events, projections, an outbox, Kafka, an inbox, process managers, a router, durable workflows, timers and a job queue all run at once, in many operating-system processes, across two databases and a broker, does a business request still reach exactly one outcome with its money and its stock accounted for — after crashes, after database and broker restarts, after network partitions, and after twenty-four hours?

After this plan a maintainer can run one command, on a laptop or on a leased GCP cell, that starts a miniature two-service system built only from the pinned runtime cohort: a "shop" bounded context and a "warehouse" bounded context, each with its own PostgreSQL server, joined by two Kafka topics, and run as roughly two dozen child processes of the single `kenshou` binary. A seeded driver pushes open-loop order traffic through it. The run ends with verdict files stating whether every accepted order reached exactly one terminal state, whether money and stock were conserved across the two contexts, whether anything was left orphaned in an outbox, inbox, workflow, timer or queue, and whether one trace survived every hop. The same system can then be attacked (`kenshou run runtime/workers/concurrency/sigkill-role --set fault.victim-role=b-resume`), soaked in gated stages of one, four and twenty-four hours with a leak verdict per process, benchmarked for order-to-terminal latency and sustained throughput, and measured with all telemetry off versus production-like tracing and scraped metrics.

You can see it working when `kenshou run runtime/order-flow/correctness/happy-path --out runs` exits 0, the run directory contains one log file per worker process and one verdict file per invariant, and the same scenario fails with a readable counter-example when the unit-tested doctored-data check injects a double capture.

## Decision Log

- Decision: Build a purpose-made reference system inside `kenshou-runtime` on the current cohort, and treat `mori://shinzui/keiro-runtime-jitsurei` only as a shape.
  Rationale: That repository is pinned to Keiro 0.3 with `file://` source pins, runs its workers as one-shot invocations, shares a machine-global Redpanda, and uses `deterministicAwakeableId`, which no longer exists in keiro 0.17 (awakeable identifiers are now opaque and journaled). The current-cohort reference is the `jitsurei` package inside the keiro repository, which this plan uses as its coding model.
  Date: 2026-09-20

- Decision: Model money (shop) and stock (warehouse) as two instances of the account-ledger aggregate that `docs/plans/12-cover-the-keiro-command-processor-process-managers-and-routers.md` owns, and add only three small aggregates here (order, fulfilment, saga log).
  Rationale: The MasterPlan requires the assembled system to reuse the keiro fixture domain; one ledger aggregate used twice gives conservation invariants in both contexts without a second balance-carrying transducer.
  Date: 2026-09-20

- Decision: Exactly two modules may import another layer package: `Kenshou.Suite.Runtime.System.Ledger` imports `Kenshou.Suite.Keiro.Fixture.*` and `Kenshou.Suite.Runtime.System.Broker` imports `Kenshou.Env.Kafka`.
  Rationale: The dependency plans were drafted concurrently; confining each dependency to one seam makes any signature mismatch a one-file fix. The completed plan `docs/plans/12-cover-the-keiro-command-processor-process-managers-and-routers.md` delivers the fixture as the modules `Kenshou.Suite.Keiro.Fixture.Domain`, `.Account`, `.Transfer`, `.Bonus`, `.Projection`, `.Model`, `.Workload`, `.Oracle`, `.Runtime`, `.Roles` and `.Bridge` (account-ledger aggregate, transfer saga process manager, bonus router, projections, pure model, seeded workload, SQL oracles including `money-is-conserved`, and `submitAccountCommand`); read its Milestone 1 and its Interfaces and Dependencies section first and reconcile the names assumed here against the real exports before writing anything else.
  Date: 2026-09-20

- Decision: Every command issued from an at-least-once context (workflow step, job handler, timer fire action, inbox handler) goes through `Keiro.ProcessManager.dispatchDeduplicatedCommand` or `Keiro.Inbox.Delegated.delegatedCommand` with a deterministic event identifier.
  Rationale: A re-run after a crash re-decides the command against state that the first run already changed; probing the target stream for the deterministic identifier first is the runtime's own answer, and a reference system that skipped it would report its own bugs as runtime defects.
  Date: 2026-09-20

- Decision: No business outcome depends on a ledger command being rejected. Refusal is decided purely from the inbound message against a static catalogue; the generator guarantees funds and stock suffice; any ledger rejection is an invariant violation that halts the worker (`RejectedHalt`).
  Rationale: A rejected command leaves no durable receipt, so a redelivery could decide differently; keeping rejections out of the design keeps every outcome replay-stable.
  Date: 2026-09-20

- Decision: The Kafka consumers default to a crash-only transient policy (bounded in-place retry, then process exit and supervised restart); the house-pattern `AckRetry` policy is exercised by a dedicated known-defect scenario.
  Rationale: keiro MasterPlan 18 documents that consecutive fast `AckRetry` decisions can seek past an unprocessed record (KFK-1) and run buffered successors out of order (KFK-2) in shibuya-kafka-adapter 0.9.0.1. With `AckRetry` as the default, every database-outage scenario would be red for one known reason and nothing else would be attributable.
  Date: 2026-09-20

- Decision: The outbox publisher defaults to one acknowledged `produceMessageSync` per record; the batch-enqueue wiring is a known-defect scenario.
  Rationale: KFK-3 in the same MasterPlan: no shipped API reports broker acknowledgements for a batch, so the obvious batch wiring marks rows `sent` that the broker never acknowledged.
  Date: 2026-09-20

- Decision: Standard-tier scenarios run with a `short` lease and timeout profile; the four-hour and twenty-four-hour soaks default to the `production` profile.
  Rationale: The runtime has no clock abstraction, so recovery after `SIGKILL` takes as long as the lease it waits for (60 s workflow lease, 300 s outbox and timer reclamation by default). Short values keep crash scenarios under ten minutes; the long soaks verify the values services actually use.
  Date: 2026-09-20

- Decision: The set of accepted orders is read from the shop database, never from the driver's memory; the driver's ledger is a second witness.
  Rationale: A driver killed after commit and before the response has an order it never saw accepted. The durable store is the truth the invariants are about.
  Date: 2026-09-20

- Decision: The driver is the API process (it calls the command processor directly) and also hosts a terminal observer, a plain kiroku subscription on the order category, so order-to-terminal latency is measured inside one clock domain from the intended start time.
  Rationale: Avoids inventing an RPC layer that is not part of the runtime and avoids cross-process clock arithmetic in the headline figure.
  Date: 2026-09-20

- Decision: Each context gets its own PostgreSQL server locally, not two databases in one server.
  Rationale: The failure matrix restarts one context's postmaster while the other keeps running. If the kernel can provision only one environment, fall back to two databases in one server (keiro's `withFreshStores2` precedent) and label postmaster scenarios as restarting both contexts.
  Date: 2026-09-20

- Decision: Soak stages are separate scenarios, and the gate lives inside the scenario as the knob `soak.gate-run-result`.
  Rationale: The tier is a property of a scenario, not of a knob value, and no Integration Point defines gating; an in-scenario gate works identically under `kenshou run`, `kenshou execute` and on a cell.
  Date: 2026-09-20

- Decision: One worker role per runtime component and at least two processes per role by default; one sharded subscription per context carries the process manager, the router, the producer enqueue and the workflow start.
  Rationale: Killing one role must implicate one component. A single idempotent handler per event keeps the process count near two dozen instead of forty.
  Date: 2026-09-20

- Decision: The milestone list is the MasterPlan's, unchanged in count and meaning.
  Rationale: Required by the drafting brief; no sharpening was needed.
  Date: 2026-09-20

## Context and Orientation

This repository, `keiro-runtime-kenshou`, is a verification suite for the keiro runtime, a cohort of Haskell libraries: `kiroku` (an event store on PostgreSQL: append-only streams of events with optimistic concurrency, meaning an append names the stream version it expects and fails if another writer got there first), `pgmq-hs` (a client for PGMQ, a message queue made of PostgreSQL tables, where a read hides a message for a visibility timeout and the message reappears if it is not deleted in time), `shibuya` (a message-processing framework whose handlers return an acknowledgement decision), adapters that feed shibuya from PGMQ, kiroku and Kafka, and `keiro`, which builds a command processor, process managers, routers, durable workflows, timers, an inbox, an outbox and a job queue on top. When this plan was drafted the repository held no Haskell code at all. Everything this plan uses is delivered by earlier plans, all in `docs/plans/`: the kernel (`2-build-the-harness-kernel-for-scenarios-dimensions-run-specs-and-results.md`), the measurement, correctness, diagnostics and telemetry toolkits (`4-…`, `5-…`, `6-…`, `7-…`), the disposable Kafka broker (`11-cover-the-kafka-transport-edge-with-a-disposable-broker.md`) and the keiro fixture domain (`12-cover-the-keiro-command-processor-process-managers-and-routers.md`). Those plans were drafted in parallel with this one, so the signatures below are the shapes this plan needs; before writing code, read the completed plans for the exact names and adapt only the two seam modules.

Terms used throughout. A bounded context is one service with its own database and its own vocabulary; two contexts talk only through published messages. At-least-once delivery means a message may be handled more than once but is never silently dropped; every hop in this runtime is at-least-once, and exactly-once business effects are obtained by deterministic identifiers (the same input always produces the same event identifier, so a repeat is recognised as a duplicate) plus idempotent finalisation. An outbox is a table written in the same transaction as the business change and drained to the broker afterwards; an inbox is a table that remembers which messages were already handled. A process manager reacts to events by issuing commands to other streams; a router is its stateless sibling that fans one event out to a computed set of targets. A durable workflow is code whose named steps are journaled so that a restarted process replays results instead of repeating work; an awakeable is a workflow's promise that an external party completes later. A lease is a row that says who owns something until a time; an expired lease may be taken by someone else. A consumer group is a set of Kafka consumers that share a topic's partitions; a rebalance reassigns partitions when membership changes. Open-loop load means requests are issued on a schedule regardless of how fast earlier ones finished; measuring latency from the intended start time avoids coordinated omission, the error of not counting the waiting that a slow system imposes. A soak is a long run judged on drift and leaks rather than on a single number. Quiescence is the state in which the driver has stopped and every piece of work has reached a terminal state.

Prior art that was read for this plan, all read-only. The in-repository `jitsurei` package of `mori://shinzui/keiro` (project-relative path `jitsurei/`, on disk `/Users/shinzui/Keikaku/bokuno/keiro/jitsurei`; the artifact-level URI is pending because the package is unpublished) is the current-cohort model: `src/Jitsurei/FulfillmentProcess.hs` shows a process manager whose own state is a one-state aggregate that merely records what it observed, `src/Jitsurei/DurableWorkflow.hs` shows a workflow with `step`, `sleepNamed`, `awakeableNamed`, a step that publishes the opaque awakeable identifier, and a child workflow, `src/Jitsurei/ShipmentNotices.hs` shows a keiro-pgmq job whose handler receives its own database access because the job effect stack carries no kiroku `Store`, and `app/Main.hs` shows `withKirokuStore (keiroConnectionSettings connStr schema)` and hand-built shibuya `Adapter` values. `mori://shinzui/keiro-runtime-jitsurei` (`/Users/shinzui/Keikaku/bokuno/keiro-runtime-jitsurei`) supplied the topology: two services, a database each, two Kafka topics, a Kafka inbox consumer built from `runKafkaConsumer`, `kafkaAdapterWith`, `mkProcessor` and `runApp`, and an outbox publisher that converts `Keiro.Outbox.Kafka.KafkaProducerRecord` to a `hw-kafka-client` `ProducerRecord` and re-injects live trace headers with `Keiro.Telemetry.injectTraceContext`. The operations guide at `docs/user/operations.md` in `mori://shinzui/keiro` states that keiro does not supervise operating-system processes, lists the process kinds a deployment runs, and documents `keiro-ops --json` as the stable automation surface. `mori://shinzui/load-testing-infra/plans/17-kiroku-resilience-characterization-24h-soak-and-failure-injection` (never started) supplied the soak gate, the six-scenario failure matrix and the drift thresholds reused in Milestone 4.

Facts from the runtime sources that shape the design. Most keiro components are single-pass functions that the application must schedule: `Keiro.Outbox.publishClaimedOutbox`, `Keiro.Outbox.outboxMaintenancePass`, `Keiro.Timer.runTimerWorkerWith`, `Keiro.Workflow.Sleep.runWorkflowTimerWorker`, `Keiro.Inbox.Schema.garbageCollectCompleted`, `Keiro.Outbox.Schema.garbageCollectSent`. The built-in loops are `Keiro.Workflow.Resume.runWorkflowResumeWorkerWith` and `runWorkflowResumeWorkerPush`, `Keiro.Subscription.Shard.Worker.runShardedSubscriptionGroupAck`, `Keiro.Workflow.Gc.runWorkflowGcWorkerWith`, and `Keiro.PGMQ.Job.runJobWorkers`. Keiro has no Kafka dependency; `Keiro.Outbox.Kafka` and `Keiro.Inbox.Kafka` are pure record conversions and the bridge to librdkafka is application code, so this plan writes one. `Keiro.PGMQ.Runtime.withJobRuntime` opens its own connection pool, separate from the kiroku store pool. Every kiroku append serialises through one `$all` row, so write throughput per database has a ceiling that worker processes cannot raise. Crash recovery is governed by expiring leases because the runtime has no clock abstraction. Whether the build links the Hackage `hw-kafka-client` 5.3.0 or the house fork is part of the cohort: on the released cohort a consumer's fatal error is unobservable and every polled message leaks native memory.

Contracts this plan relies on, restated from the MasterPlan's Integration Points. The package is `kenshou-runtime`, its modules live under `Kenshou.Suite.Runtime.*`, its layer name is `runtime`, and it is the only package besides `kenshou-cli` allowed to depend on layer packages (`kenshou-keiro` and `kenshou-kafka`). A scenario identifier is `<layer>/<component>/<kind>/<name>` with kind one of `correctness`, `concurrency`, `soak`, `benchmark`; this plan's components are `order-flow`, `workers`, `postgres`, `broker`, `network`, `resources`, `ops` and `telemetry`. Tiers are `smoke` (under one minute), `standard` (under ten), `extended` (under an hour) and `soak` (hours); placements are `local`, `cell`, `either`. A scenario may carry a known-defect reference that turns an expected failure into a reported, non-blocking outcome. The package exports one `bundle :: LayerBundle` with its scenarios and worker roles and registers it with one import, one list element in `kenshou-cli/src/Kenshou/Cli/Registry.hs` and one `build-depends` entry in `kenshou-cli/kenshou-cli.cabal`. Dimensions are `telemetry.tracing` (`off`, `noop`, `sdk-inmemory`, `sdk-otlp`), `telemetry.metrics` (`off`, `collect`, `serve`, `serve-scraped`), `pg.durability` (`fsync-off`, `durable`) and `pg.version` (`17`, `18`); keiro requires 18, so every scenario here supports only `pg.version=18`. A run writes `<out>/<run-id>/` with `run-spec.json`, `run-result.json`, `manifest.json`, `samples/`, `series/`, `verdicts/<checker>.json`, `diagnosis/` and `logs/`. Outcomes are `passed`, `failed`, `errored`, `inconclusive`, `infrastructure-failure`, with exit codes 0, 1, 4, 3 and 4. Workers are child processes of the same binary started as `kenshou worker --role <name>`; a crash means `SIGKILL` of a process or termination of a database backend, never a thrown exception. A scenario never opens a database itself: it asks the kernel for a `PostgresEnv` migrated with one `pg-migrate` plan composed of kiroku, keiro and PGMQ.

## Plan of Work

### Milestone 1 — The two-context reference system

Scope: everything needed to start the system, push orders through it and stop it, plus one smoke scenario. At the end `kenshou-runtime` builds, its bundle is registered, `kenshou list` shows a `runtime` scenario, and `cabal run kenshou -- run runtime/order-flow/correctness/single-order-roundtrip --out runs` passes with ten orders and one process per role. Acceptance is that every one of the ten orders is `Completed` in the shop and `Shipped` in the warehouse, and that `logs/` holds files for each of the twelve long-running roles.

The business. An order names a customer, a stock-keeping unit (SKU), a quantity and an amount in cents. The shop (context A) keeps a money ledger with accounts `customer-<n>`, `escrow`, `merchant`, `loyalty-pool` and `loyalty-<n>`; the warehouse (context B) keeps a stock ledger with accounts `sku-<n>-available`, `sku-<n>-reserved` and `sku-<n>-shipped`. Both ledgers are the fixture's account aggregate. The driver submits `PlaceOrder` to the stream `order-<id>`; the event `OrderPlaced` and a row in the read model `shop.orders` commit together (an inline projection runs in the append transaction). The shop's dispatch worker, a sharded subscription over the `order` category, handles each order event idempotently: the process manager `shop-payment` moves the amount from the customer to `escrow` on `OrderPlaced`, from `escrow` to `merchant` on `OrderCompleted`, and from `escrow` back to the customer on `OrderRejected` or `OrderExpired`; the router `shop-loyalty` resolves the customer's referrers from the seeded read-only table `shop.referrals` and, on `OrderCompleted`, debits `loyalty-pool` and credits each referrer's loyalty account; and the integration producer `shop` enqueues `order.placed.v1` into the outbox with `enqueueProducerEventTx`. The shop publisher drains the outbox to the topic `<prefix>.shop.events` with the order identifier as the partition key. The warehouse consumer reads that topic through shibuya-kafka-adapter under `Serial` concurrency, decodes with `Keiro.Inbox.Kafka.integrationEventFromKafka`, and passes the event through the inbox into one command on `fulfilment-<id>`: `RequestFulfilment` for a stocked SKU, `RefuseFulfilment` for a SKU the static catalogue marks discontinued. A record that cannot be decoded is written to `warehouse.poison_records` and acknowledged. The warehouse dispatch worker handles fulfilment events: the process manager `warehouse-stock` moves the quantity from `available` to `reserved` on `FulfilmentRequested` and schedules a deadline timer in the same transaction as its own state append, moves `reserved` to `shipped` on `FulfilmentShipped`, and moves `reserved` back to `available` on `FulfilmentExpired`; after a successful reservation the handler starts the workflow `fulfilment` with `runWorkflowWith`; on a terminal event it cancels the deadline timer or the parked workflow as appropriate and enqueues `fulfilment.shipped.v1`, `fulfilment.refused.v1` or `fulfilment.expired.v1`. The workflow sleeps (`sleepNamed "cooling-off"`), allocates an awakeable (`awakeableNamed "pick-confirmation"`), runs the step `request-pick` that upserts `warehouse.pick_requests` and enqueues a `PickJob` into a keiro-pgmq FIFO group keyed by SKU, awaits the awakeable, and runs the step `ship`, which dispatches `ShipFulfilment`. The pick job handler calls `signalAwakeable`; for the seeded fraction of orders flagged `slowPick` it returns `Done` without signalling, so the deadline timer fires and its fire action dispatches `ExpireFulfilment`. The fulfilment aggregate is the serialisation point: whichever of `ShipFulfilment` and `ExpireFulfilment` appends first wins, the other is recognised as already decided. The warehouse publisher sends outcomes to `<prefix>.warehouse.events`; the shop consumer turns them into `CompleteOrder`, `RejectOrder` or `ExpireOrder`.

The Kafka bridge has two halves. The publish function has the type that `publishClaimedOutbox` expects, `[OutboxRow] -> Eff es [(OutboxId, PublishOutcome)]`; it converts each row with `outboxRowToKafkaRecord`, replaces stored trace headers with the live producer span's context, and in the default mode calls `Kafka.Effectful.Producer.produceMessageSync` once per row inside a long-lived `runKafkaProducer` (or `runKafkaProducerTraced` when a tracer is present), mapping a returned offset to `PublishSucceeded` and a `KafkaError` to `PublishFailed`. The consumer runs `runKafkaConsumer` (or `runKafkaConsumerTraced`) with `noAutoOffsetStore`, the run's group identifier and any `kafka.prop.*` properties, builds the adapter with `newKafkaAdapterState` and `kafkaAdapterWith`, installs `kafkaRebalanceHandler`, and runs one processor with `mkProcessor` under `runApp defaultAppConfig`. Its handler returns `AckOk` after a processed or duplicate inbox result and after a persisted poison record. On a transient database error the default `crash-only` policy retries in place three times with backoff and then exits the process with a distinct exit code, so the supervisor restarts it and consumption resumes from the committed offset; the `ack-retry` policy returns `AckRetry (RetryDelay 5)` instead. Inbox idempotence is a knob: `table` uses `runInboxTransactionWithRetries`, whose transaction inserts the message into the application table `intake` (primary key: message identifier), after which the same handler dispatches the command with `dispatchDeduplicatedCommand` under the identifier `delegatedEventId consumer source dedupeKey target operation` and marks the intake row dispatched, and a sweep at consumer start dispatches any intake row left undispatched by a crash; `delegated` uses `runInboxDelegatedWithRetries` with `delegatedCommand` and writes no inbox rows.

### Milestone 2 — End-to-end correctness invariants

Scope: the oracles that every later milestone reuses, and six correctness scenarios. At the end `cabal run kenshou -- run runtime/order-flow/correctness/happy-path --out runs` writes eight verdict files and passes, and `cabal test kenshou-runtime-test` proves each checker fails on doctored data. New files: `src/Kenshou/Suite/Runtime/Oracle.hs`, `Runtime/Oracle/Sql.hs`, `Runtime/Ops.hs`, `Runtime/Correctness/OrderFlow.hs`, `Runtime/Correctness/Telemetry.hs`, `Runtime/Correctness/Ops.hs`.

The oracles never hold all orders in memory. Each invariant is a SQL query per context returning a violation count and the first twenty examples; cross-context comparisons export `(orderId, terminal kind, quantity, amount)` from each database in key order and merge-join the two files with the correctness toolkit's external merge. Truth comes from tables written in the append transaction (`shop.orders` carries `status` and a `terminal_count` incremented by every terminal event; the ledger entries table carries the transfer reference), and `oracle.sample-size` (default 200) orders are re-read directly from their streams through kiroku's public read API to confirm that the tables agree with the events.


The invariants, with their class (a `contract` invariant is promised by the documentation and blocks; an `implementation` invariant is an observed property and is reported). I1 `terminal-exactly-once` (contract): every order with an `OrderPlaced` event has exactly one terminal event within the quiescence deadline, never two, and the shop's terminal kind matches the warehouse's (`Completed` with `Shipped`, `Rejected` with `Refused`, `Expired` with `Expired`). I2 `effects-exactly-once` (contract): per order exactly one hold pair (one debit and one credit under reference `<id>:hold`), exactly one of capture or refund, exactly one reserve pair if and only if fulfilment was requested, exactly one of commit or release, and for a completed order exactly one loyalty debit and `runtime.router-fanout` loyalty credits; zero ledger rejections and zero rows in `keiro.keiro_dead_letters`. I3 `conservation` (contract): in the shop the sum of all balances equals the seeded total, `escrow` is zero at quiescence and `merchant` equals the captured amounts; in the warehouse `available + reserved + shipped` equals the seeded stock per SKU and `reserved` is zero at quiescence; across contexts the quantity shipped equals the quantity of completed orders and the captured amount equals the amount of shipped fulfilments. I4 `no-orphans` (contract): in both databases no outbox row is `pending`, `publishing` or `failed` and none is `dead` or `rejected`; no inbox row is `processing` or `failed`; no intake row is undispatched; no workflow is `running`, `suspended` or `failed`; no timer is `scheduled`, `firing` or `dead`; no awakeable is pending; the pick queue and its dead-letter queue are empty; `kiroku.dead_letters` is empty; every subscription member's checkpoint has reached the store position; and both consumer groups have zero lag. I5 `duplicates-bounded` (contract): redeliveries observed at each hop (inbox duplicates, process-manager duplicates, job re-reads, step re-executions) fall inside a declared window, a fault window extended by the relevant lease or commit interval, or the consumer-group start-up window; outside them the count is zero. I6 `checkpoints-monotonic` (contract): subscription checkpoints sampled every five seconds never decrease. I7 `trace-continuity`, evaluated only when `telemetry.tracing` is `sdk-inmemory` or `sdk-otlp`: contract class for the documented hops (the outbox row has a `traceparent`; the consumer's process span is a child of the publisher's `send <topic>` span, in both directions; the job's `pick process` consumer span shares the trace of the step that enqueued it with `enqueueTraced`), implementation class for the fraction of sampled orders whose whole journey is a single trace. I8 `ops-cross-check` (contract): `keiro-ops --json` agrees with direct SQL for `outbox backlog`, `inbox backlog`, `wf list --status …`, `timer stuck list`, `shard status`, `stream subscriptions` and `pgmq dlq read`.

Scenarios, all placement `either`, all four values of both telemetry dimensions, both `pg.durability` values. `runtime/order-flow/correctness/happy-path` (tier `standard`): default knobs with both fractions 0; oracle I1 to I6 with every order `Completed`. `runtime/order-flow/correctness/mixed-outcomes` (`standard`): `runtime.refuse-fraction=0.2`, `runtime.expire-fraction=0.1`, `runtime.fulfilment-deadline-seconds=5`; oracle I1 to I6, and the observed outcome mix must equal the mix the seed predicts. `runtime/order-flow/correctness/completion-expiry-race` (`standard`): `runtime.cooling-off-ms` equal to the deadline so shipping and expiry race for every order; oracle I1 and I3 (no order both shipped and released, no order neither). `runtime/order-flow/correctness/duplicate-submission` (`standard`): two driver processes submit the same seeded orders three times each; oracle adds exactly one `OrderPlaced` per order. `runtime/telemetry/correctness/trace-continuity` (`standard`, only `telemetry.tracing` in `sdk-inmemory`, `sdk-otlp`): oracle I7 over 100 sampled orders. `runtime/ops/correctness/keiro-ops-cross-check` (`standard`): stops the publishers to build an outbox backlog, injects one undecodable Kafka record and one pick job with a blank identifier so a dead-letter entry exists, pauses all roles with `SIGSTOP`, and evaluates I8 on the frozen state. `happy-path` declares `runtime.inbox-idempotence`, `workflow.wake` and `outbox.ordering-policy` as variants for the planner to expand.

### Milestone 3 — The whole-runtime failure matrix

Scope: each failure a production deployment meets, injected while orders are flowing, and judged by the Milestone 2 invariants. At the end thirteen fault scenarios and two known-defect scenarios exist under `src/Kenshou/Suite/Runtime/Concurrency/` (`Workers.hs`, `Postgres.hs`, `Broker.hs`, `Network.hs`, `Resources.hs`). Acceptance: `cabal run kenshou -- run runtime/workers/concurrency/sigkill-role --set fault.victim-role=b-resume --out runs` exits 0 and its result records at least one kill and one restart. All require `pg.durability=durable` and default to `runtime.duration-seconds=180` at 20 orders per second.

Every scenario follows one procedure: start the system, mark the warm-up phase for 30 s, mark the steady phase, run the fault schedule, stop the driver, lift all faults, await quiescence, stop the roles, run `verifyEndToEnd` with the recorded fault windows. Every scenario is non-vacuous: it records evidence that the fault took effect (signals delivered and processes restarted, backends terminated, bytes refused by the proxy, broker down time) and reports `errored` if there is none. The stall watchdog is armed throughout; a stall with no active fault captures thread dumps and the lock graphs of both databases and fails the run. Shared fault knobs: `fault.period-seconds` integer 20, `fault.count` integer 5, `fault.context` (`a`, `b`, `both`; default `b`), `fault.outage-seconds` integer 20.

`runtime/workers/concurrency/sigkill-role` (`standard`, `either`): `fault.victim-role` names any role, default `b-resume`, with every role declared as a variant; one process of the role is killed every period and restarted with backoff. The oracle is I1 to I6; the duplicate window is the role's lease (workflow lease for `b-resume`, shard lease for the dispatchers, publishing timeout for the publishers, visibility timeout for `b-jobs`, the auto-commit interval plus in-flight messages for the consumers). `runtime/workers/concurrency/sigkill-storm` (`extended`): a seeded schedule kills a random process of a random role every 15 s for eight minutes, including the driver. `runtime/workers/concurrency/paused-lease-holder` (`standard`): `SIGSTOP` a shard owner and a resume worker for twice the lease, then `SIGCONT`; the zombie may duplicate deliveries but I2 and I6 must hold, and the disjoint-ownership checker must show overlap only inside the declared window. `runtime/workers/concurrency/rolling-restart` (`standard`): `SIGTERM` each process in turn; graceful relinquish must make takeover faster than lease expiry, which is recorded, and I5 allows duplicates only in the restart windows.

`runtime/postgres/concurrency/backend-kill` (`standard`): `fault.target` (`pool`, `listener`, `all`; default `all`) selects ordinary pooled backends, the LISTEN connections that feed push wake-up, or both, by `application_name`; with the listener killed the fallback poll must keep workflows moving. `runtime/postgres/concurrency/postmaster-restart` (`standard`): `fault.restart-mode` (`fast`, `immediate`; default `immediate`) restarts one context's server; the oracle adds that every order the driver recorded as accepted exists after the restart. `runtime/broker/concurrency/broker-restart` (`standard`): the broker is killed and restarted after the outage; outbox rows wait as `failed` with backoff and none becomes `dead`. `runtime/network/concurrency/partition-database` (`standard`): `fault.mode` (`reset`, `blackhole`, `latency`; default `blackhole`) on the proxy between one context's workers and its database; `blackhole` exercises timeouts rather than refused connections. `runtime/network/concurrency/partition-broker` (`standard`): the same modes on the proxied broker listener for one context. `runtime/resources/concurrency/pool-starvation` (`standard`): `kiroku.pool-size=2`, `workflow.max-concurrent-advances=16`, and a lock holder blocking one ledger account for ten seconds in each period; the system must keep making progress and the watchdog must not classify a persistent `deadlock` or `pool-starvation`. `runtime/resources/concurrency/slow-consumer-backpressure` (`extended`): the warehouse consumer and pick handler gain `fault.latency-ms` (default 250) for five minutes while the driver keeps its rate; backlog must accumulate as consumer lag and queue depth, the live bytes of every process must stay bounded, and the system must drain afterwards. `runtime/resources/concurrency/memory-limit` (`standard`, placement `cell`): a memory ceiling on one role until the kernel kills it, judged like `sigkill-role`. `runtime/resources/concurrency/disk-full` (`extended`, placement `cell`): the data volume of one context is filled and then freed; commands fail while it is full, nothing acknowledged is lost, and the system recovers without operator action.

Two scenarios carry a known-defect reference and are reported without blocking. `runtime/broker/concurrency/ack-retry-under-database-outage` (`standard`) sets `runtime.kafka-transient-policy=ack-retry` and takes the warehouse database away for 20 s with the consumer's inbox full; I1 is expected to fail on the released cohort with orders that never reach the warehouse; reference `mori://shinzui/keiro/plans/119-fix-the-seek-barrier-ordering-and-stale-successor-execution-in-shibuya-kafka-adapter`. `runtime/broker/concurrency/batch-enqueue-publish-under-broker-restart` (`standard`) sets `runtime.publish-mode=batch-enqueue` and restarts the broker; rows marked `sent` whose records the broker never stored are expected; reference `mori://shinzui/keiro/plans/120-add-an-acked-batch-publish-api-to-kafka-effectful-and-a-reference-outbox-bridge`. Both must pass once the cohort contains the fix, at which point the reference is removed.

### Milestone 4 — Gated soaks of one, four and twenty-four hours

Scope: long runs under steady load, and under restart churn, judged on four things together. At the end six soak scenarios exist in `src/Kenshou/Suite/Runtime/Soak/` (`Steady.hs`, `Churn.hs`, `Audit.hs`, `Gate.hs`), and the two reduced ones have been run locally with their outcomes recorded in this plan. Acceptance: `steady-reduced` passes locally in about thirty minutes with a `stable` leak verdict for every process, and `steady-4h` refuses to start without a passing `steady-1h` result.

A soak passes only if all four judgements pass. First, a leak verdict per process from the diagnostics toolkit over live bytes after major garbage collection, Haskell threads, operating-system threads, file descriptors and PostgreSQL connections per `application_name`, after a warm-up cut of `soak.warmup-minutes` (default 10); `insufficient-data` makes the run `inconclusive`. On a cohort that links the Hackage `hw-kafka-client`, the native-memory series of the two consumer roles is reported with class `implementation` and the upstream reference `mori://shinzui/keiro/masterplans/23-make-the-kafka-consumer-streaming-stack-surface-fatal-errors-and-close-deterministically`, because the message leak is known there; on the head cohort it blocks. Second, invariants I1 to I6 at final quiescence. Third, growth bounds sampled every minute: with the maintenance roles running at `maintenance.retention-seconds` (default 600), the row counts of `keiro_outbox`, `keiro_inbox`, `keiro_workflows`, `keiro_workflow_steps`, `keiro_awakeables`, the intake tables and the PGMQ queue and archive tables must plateau (robust slope not above zero after warm-up); kiroku's event tables may grow linearly within ten percent of orders multiplied by events per order; dead tuples in each named table must stay below twenty percent of live tuples; topic size must stay under the retention configured at creation. Any table that has no garbage collector in the runtime (fired rows in `keiro_timers` are the candidate) is reported as an observation with its slope, and an improvement request is filed upstream instead of failing the soak. Fourth, steady-state drift in ten-minute windows, comparing the last hour with the first hour after warm-up: order-to-terminal p99 may grow by at most 25 percent, throughput may fall by at most 10 percent, and garbage-collection pause p99 may grow by at most 20 percent.

A rolling audit runs every `soak.audit-interval-minutes` (default 10) so that a failure at hour two is known at hour two: no accepted order older than `soak.max-order-age-seconds` (default 120) without a terminal state while no fault is active, no `dead` or `failed` row anywhere, growth bounds and an interim leak verdict. With `soak.fail-fast=true` (default) a violation stops the run and saves the evidence. The ledger files and every oracle are streaming, so the harness itself stays bounded.

The scenarios. `runtime/order-flow/soak/steady-reduced` (tier `extended`, `either`, 30 minutes, `short` profile) and `runtime/order-flow/soak/churn-reduced` (`extended`, `either`, 40 minutes, the `sigkill-storm` schedule every 60 s plus a backend kill every 5 minutes) are the local forms. `runtime/order-flow/soak/steady-1h` (`soak`, `either`), `steady-4h` and `steady-24h` (`soak`, `cell`) and `churn-4h` (`soak`, `cell`) default to the `production` profile and 50 orders per second. The gate: `steady-1h` requires a passed `steady-reduced`, `steady-4h` a passed `steady-1h`, `steady-24h` a passed `steady-4h`, `churn-4h` a passed `churn-reduced`. The knob `soak.gate-run-result` names the earlier stage's `run-result.json`; the scenario checks the scenario identifier, the outcome `passed`, an identical resolved cohort identity including the solver plan hash, identical knobs other than duration, and an age under `soak.gate-max-age-hours` (default 168), and otherwise ends `errored` with the reason. `soak.skip-gate=true` overrides the check and is recorded in the result.

### Milestone 5 — End-to-end benchmarks and whole-system telemetry overhead

Comparisons are paired and interleaved with at least three trials per arm by the measurement toolkit. Acceptance: `order-to-terminal-latency` writes `samples/order-to-terminal.hist` and a summary with p50, p90, p99, p99.9 and maximum, and `kenshou overhead runtime/telemetry/benchmark/whole-system-overhead` produces a `kenshou.overhead-report/v1`.

`runtime/order-flow/benchmark/order-to-terminal-latency`: open loop at `runtime.rate-per-second` (default 50); the headline is the latency from the intended submission time to the terminal order event seen by the driver's observer; per-hop wall-clock timestamps recorded by the workers (placed, enqueued, published, consumed, reserved, picked, shipped, completed) are summarised as diagnostics only; an open-loop backlog that grows makes the run `inconclusive`. `runtime/order-flow/benchmark/sustained-throughput`: steps the rate through `bench.rate-steps` (default `25,50,100,200,400`), two minutes each, and reports the highest rate at which backlog stays bounded and p99 stays under `bench.slo-p99-ms` (default 5000). `runtime/order-flow/benchmark/scaling-with-worker-processes`: variants `runtime.processes-per-role` 1, 2, 4, 8 at the rate found above; reports throughput, p99 and scaling efficiency; no threshold, because the `$all` append lock bounds each database and the result is a characterisation. `runtime/telemetry/benchmark/whole-system-overhead`: arm A is `telemetry.tracing=off` with `telemetry.metrics=off`; arm B is `telemetry.tracing=sdk-otlp` with `telemetry.metrics=serve-scraped` at the production scrape interval, every process serving and scraped; metrics are throughput, order-to-terminal p50 and p99, processor time and allocation rate per process, and scrape latency; budgets are added to `policies/telemetry-overhead.json` under the key `runtime`. Measurement never flows through the telemetry being toggled.

`docs/layers/runtime.md` lists every scenario with its knobs, tier, placement and what it proves, draws the two-context diagram in text, and explains how to read a failed I1 to I8 verdict back to a component and which layer scenario from `docs/plans/11-…` to `docs/plans/14-…` to run next.

## Validation and Acceptance

Milestone 1 is accepted when the smoke scenario passes, `runs/<id>/logs/` contains one stdout and one stderr file per process, `psql` against either context shows rows in `shop.orders` or `warehouse.pick_requests`, and no process, topic or consumer group with the run's prefix remains afterwards (`pgrep -f 'kenshou worker'` prints nothing).

Milestone 2 is accepted when `happy-path`, `mixed-outcomes`, `completion-expiry-race` and `duplicate-submission` pass with the same seed twice and produce identical outcome mixes; when `cabal test kenshou-runtime-test` shows each checker failing on its doctored input (a second capture row fails I2 and I3, a deleted terminal event fails I1, a `pending` outbox row fails I4, a decreased checkpoint fails I6, a severed `traceparent` fails I7, an altered backlog count fails I8); and when `keiro-ops-cross-check` reports every compared command with equal values.

Milestone 3 is accepted when every fault scenario passes on the head cohort with recorded fault evidence, when disabling the injector (unit-tested with a no-op schedule) makes the scenario `errored` rather than `passed`, and when the two known-defect scenarios report their outcome with the upstream reference and do not change the exit code of a run plan. A failure here is a finding: reproduce it with `--seed`, run the matching layer scenario, and file it against the owning repository.

Milestone 4 is accepted when `steady-reduced` and `churn-reduced` pass locally with `stable` verdicts, when `steady-4h` without a gate result ends `errored` naming the missing stage, when a gate result from a different cohort is refused, and when the seeded leaking worker of the diagnostics self-tests, substituted for one role in a unit-level run, turns the soak `failed`. The one-, four- and twenty-four-hour stages are accepted on a cell through `docs/plans/17-…`; until a cell exists, `steady-1h` is run locally and labelled non-authoritative.

Milestone 5 is accepted when two back-to-back runs of `order-to-terminal-latency` compare as `pass` under `kenshou compare`, when an injected 50 ms sleep in the warehouse consumer compares as `regression`, when `sustained-throughput` reports a rate and marks the first overloaded step, and when the overhead report contains a delta and a verdict for every metric. The whole plan is accepted when `kenshou list` shows all thirty-two `runtime` scenarios (one in Milestone 1, six in Milestone 2, fifteen in Milestone 3, six in Milestone 4, four in Milestone 5), the smoke and standard tiers pass locally on both cohorts apart from known defects, `docs/layers/runtime.md` exists, and `okf validate docs/adr --strict --profile docs/adr/profile.dhall --profile-enforce --log-enforce` passes.


## Idempotence and Recovery

Every run creates its own PostgreSQL servers, its own broker or its own prefixed topics and groups, and its own run directory, so any scenario can be repeated at any time and no run writes into another's directory. `withReferenceSystem` releases resources in a `finally` and additionally places all workers in one process group that is killed on exit, because a `SIGKILL` of the harness itself skips Haskell cleanup. If the harness is killed, recover with `pkill -f 'kenshou worker'`, remove stale ephemeral PostgreSQL directories as the kernel plan describes, and delete leftovers on an external broker with the fixture's clean-up helper using the run's prefix, which is printed in `run-spec.json`. The application DDL, account seeding, queue provisioning (`ensureOrderedJobQueue`) and shard row creation are idempotent. A driver restarted mid-run resumes from its high-water mark and resubmits with the same event identifiers, which the store treats as duplicates. Soaks with `soak.fail-fast` leave a complete run directory at the moment of failure; a soak interrupted by the operator is `errored`, never `passed`, and cannot satisfy a gate. On a cell, clean-up of machines and buckets belongs to the cell protocol; this plan only guarantees that its processes exit and its topics are removed. Code changes are additive to one new package plus the three-line registration, so reverting the registration removes the layer from the binary without touching any other layer.
