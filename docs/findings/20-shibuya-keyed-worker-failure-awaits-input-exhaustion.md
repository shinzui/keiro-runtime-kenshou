# Historical keyed scheduler defers a worker failure

Status: implementation finding reproduced on released `shibuya-core` 0.9.0.3 and fixed on Hackage 0.10.0.0. Owner request: `mori://shinzui/shibuya/okf/improvement-requests/concepts/IR-6`; owner review: `mori://shinzui/shibuya/okf/reviews/concepts/REV-5`. No owner bug report is warranted by the published public contract evidence.

`shibuya/core-ordering/concurrency/keyed-worker-failure-stops-intake` calls `Shibuya.Internal.Runner.KeyedScheduler.runKeyedScheduler` directly. The first worker throws while the input stream remains unending. Released run `runs/01a0e46f-95f7-706a-9eac-abb191b92b90/run-result.json` reproduced `REV-5-F1` and the successor-start bound failure. Pinned head passed at `runs/01a0e47c-4105-73da-97c6-82180ca2d138/run-result.json`; the isolated Hackage 0.10.0.0 CLI passed at `runs/01a0e44f-4b23-757a-9a65-8806d028f193/run-result.json`. These run paths are local to this repository.

Published `mori://shinzui/shibuya/okf/capabilities/concepts/CAP-5` promises per-key processing and acknowledgement order and cross-key concurrency. It does not specify how this internal scheduler surfaces a raw worker exception. Owner REV-5 says handler and finalizer exceptions normally pass through runner translation, so its direct scheduler probe does not establish that the public `runApp` path breaches a failure-propagation contract. IR-6 requests prompt propagation and cleanup for the internal path. The scenario remains a versioned regression probe with its review reference; its historical failure is not counted as a public-contract bug report.
