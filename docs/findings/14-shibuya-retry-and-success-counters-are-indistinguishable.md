# Shibuya retry and success counters are indistinguishable

Status: reproduced on historical `shibuya-metrics` 0.9.0.3, pinned remediation, and the isolated Hackage 0.10.0.0 package lane. This is an implementation finding, not a broken published contract. Owner request: `mori://shinzui/shibuya/okf/improvement-requests/concepts/IR-8`.

`shibuya/metrics/correctness/counters-distinguish-retries-from-success` runs two processors against independent synthetic brokers. One handler returns `AckRetry (RetryDelay 60)` and the other returns `AckOk`. The brokers report different decisions, but both JSON `stats` report received 1, processed 1 and failed 0, and all processor-labelled Prometheus samples match after normalizing the processor label. The historical sealed result is in `runs/01a0da56-3ecc-71df-a3d5-c5321ccfcee1/run-result.json`; that revision incorrectly marked this observation as the known defect `REV-7-A2`. The scenario's revision 2 checks the published mapping and records `retry-success-counters-indistinguishable` under `summaries.verdicts.retry-counter-truthfulness.implementationFindings` without failing the run.

Revision-2 historical run `runs/01a0dac4-cd4a-7491-9a2d-caa464890139/run-result.json` and pinned-head run `runs/01a0dac3-2f43-77c8-b3e7-d2795f467ac6/run-result.json` sealed with `outcome: passed`, no known defect, empty contract failures, and the visibility gap under `implementationFindings`.

The owner architecture at `mori://shinzui/shibuya/docs/architecture` project-relative `METRICS.md` and `MESSAGE_FLOW.md` explicitly says both decisions increment `processed` and neither increments `failed`; artifact-level URIs for those files are pending Mori coverage. The probe's direct public metrics-handle control checks success, retry, dead-letter, handler exception and halt mappings. A separate retry-decision count would improve operations without silently redefining the current counter. IR-8 requests that additive metric and a precise account of what it measures.
