# Broker-backed Kafka scenarios were routed to brokerless cells

Status: reproduced in the released Kenshou catalog and repaired in this repository. This is a harness routing defect, not a Kafka runtime-owner bug report.

The released-cohort `kafka/adapter/concurrency/barrier-overwrite` cell attempt, session `01a0eed2-fc94-74ed-a097-9661c0fa28ea`, passed route preparation for alpha even though the cell descriptor has no broker image and its runtime environment reported `broker: null`. The cell slice completed and verified, but nested run `01a0eec5-04ec-7388-8fc6-4bb186d22cdb` errored before the defect probe: a private Redpanda broker needs Apple Container or Docker, neither of which is available to the Linux cell payload. This run is an infrastructure/catalog failure and supplies no evidence for `mori://shinzui/shibuya-kafka-adapter/okf/bug-reports/concepts/BUG-5`.

The catalog had set `requires = noEnvironment` for all broker-backed Kafka scenarios. That suppressed both the cell route's broker-image check and the execution adapter's external-broker binding. The pure Kafka model is the only scenario group that does not need a broker. The catalog now gives every broker-backed scenario `kafkaEnvironment`, and a package test checks the complete registered bundle. `cabal test -j1 kenshou-kafka:test:kenshou-kafka-test` passed six examples. Route preparation of the same plan now writes `.dev/kafka-barrier-cell-route-after-fix/unroutable.json` with `NeedsBrokerButCellHasNone` for the nested run, before submission. A clean released-cohort reproduction of BUG-5 remains open until a broker-capable cell is available or a controlled local correctness run is selected; the workstation is too busy for local performance measurements.

Update (2026-10-03): the controlled local correctness run was selected instead of waiting for a broker-capable cell. Released-cohort run `01a10031-f68b-730b-bbeb-add4fcde7283` ran from a clean tree at `741434f` under the shared host lock and reproduced the predicted BUG-5 counter-example: a first delivery of offsets 0–9, redelivery of only 4–9, a committed offset of 10, and no successful decision for offset 3. The result was `barrier-overwrite-no-loss`, known defect `reproduced` and nonblocking. A cell reproduction still needs plan 16's broker role.

Update (2026-10-03, broker-capable cell): plan 16 added a Redpanda v26.2.1 broker to `cell-alpha`. Kenshou `b9881d1` published released payload bundle `d762e4e64d5bf71fe70b78cff823ec97f264d5965124e06a0c12379119374ec1`. Route preparation of a fresh plan for `kafka/adapter/concurrency/barrier-overwrite-loses-record` admitted nested run `01a10213-b750-723b-b7bc-b131783b7071` to alpha with no `NeedsBrokerButCellHasNone` refusal. That confirms the catalog repair against a real broker descriptor. Cell run `01a10247-5864-74db-9978-1c73f6b232fe` received a verified broker reset and a broker environment, then sealed `completed` and verified (manifest SHA-256 `ccb902b17373ae45e2607fc65d69d3463005393bcb788c542cddca3df8da77b1`, session journal `.dev/ep16-broker/cell-runs/ep16-kafka-barrier-broker/session.json`, local and untracked).

The nested run still errored with exit code 4, before the defect probe. Its known-defect status is `not-reproduced`, and it supplies no evidence for BUG-5. The external-broker path runs `rpk` from `PATH` (`Kenshou.Env.Kafka.Admin.runRpk`), but the Kenshou payload closure contains no redpanda client. On the cell, the call reached the driver image's `rpk` 26.1.7, which rejects `rpk group list --format json` with `unknown flag: --format`. Local runs use the dev shell's `rpk` 26.2.2. This is a second harness defect in the same routing path: the payload depends on an ambient tool that the cell does not version. It is not a Kafka runtime-owner bug. A cell reproduction of BUG-5 needs the payload to carry its own `rpk` (or the harness to stop depending on unsupported flags) and then a rerun of this plan.
