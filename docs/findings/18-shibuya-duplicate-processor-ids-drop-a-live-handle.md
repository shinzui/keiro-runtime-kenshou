# Historical duplicate processor IDs drop a live Shibuya handle

Status: reproduced on the released `shibuya-core` 0.9.0.3 cohort and fixed on Hackage 0.10.0.0. Owner report: `mori://shinzui/shibuya/okf/bug-reports/concepts/BUG-2`.

`shibuya/core-runner/correctness/duplicate-processor-ids-are-rejected` gives `runApp` one ordinary and one batch processor with the same `ProcessorId`. The released run `runs/01a0cefa-42e2-730d-8528-20619beecaa7/run-result.json` records `REV-3-F2`: startup was accepted and a source was pulled. The later released sweep `runs/01a0e478-fc24-7455-b29b-552eccf2dadb/run-result.json` reproduced the same scoped failure. A clean released-cohort run at harness revision `725bae6`, `runs/01a0e52d-7866-7793-bfb0-8a96410bc38c/run-result.json`, reproduced `REV-3-F2` with owner BUG-2 as the nonblocking known-defect reference; its run-result schema validated. Pinned head passed at `runs/01a0e485-6fcf-7394-8c5e-ab3b343c6914/run-result.json`, and the isolated 0.10.0.0 CLI passed at `runs/01a0e458-680b-732d-8c5d-fdbb283c0502/run-result.json`. These run paths are local to this repository.

The owner capability `mori://shinzui/shibuya/okf/capabilities/concepts/CAP-3` promises that `runApp` manages a list of named processors and returns a handle for introspection and shutdown. Owner review `mori://shinzui/shibuya/okf/reviews/concepts/REV-3` observed that the 0.9.0.3 construction starts both processors but keeps only the last handle in a map keyed by ID, leaving the first adapter without a shutdown call. This violates the named-processor ownership promise, beyond the validation preference itself. Owner request `mori://shinzui/shibuya/okf/improvement-requests/concepts/IR-6` asked for duplicate-ID rejection, which the 0.10.0.0 scenario verifies. The owner report is marked fixed for 0.10.0.0 and does not describe a current-release failure.
