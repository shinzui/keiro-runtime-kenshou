# PGMQ long polls can starve acknowledgement on a shared pool

Status: reproduced against historical `shibuya-pgmq-adapter` 0.16.0.0 and current Hackage 0.16.1.0 on PostgreSQL 17 and 18, and the pinned remediation checkout on PostgreSQL 18. Owner bug report: `mori://shinzui/shibuya-pgmq-adapter/okf/bug-reports/concepts/BUG-1`.

`shibuya/pgmq-adapter/concurrency/long-poll-pool-starvation` runs two processors with `LongPolling 5 100` on a shared Hasql pool with two connections. A separate producer pool sends one message to each source queue after PostgreSQL reports two active `pgmq.read_with_poll` calls. The handlers each run once, returning `AckOk` and `AckDeadLetter` to a direct DLQ. The SQL oracle uses the producer pool so it cannot consume either of the two consumer connections.

At the 25-second deadline in the historical PostgreSQL 18 run `runs/01a0db9c-0dcb-70e4-a6ee-43c1f110d26d/run-result.json`, the source queues still hold one row each, the DLQ has zero rows, and two long polls are active. `onAckFailure` has not fired. `stopAppGracefully` subsequently lets both acknowledgements finish: both source queues empty and the DLQ has one row. The run therefore proves stalled acknowledgement progress while the application is live; it does not show message loss. Historical PostgreSQL 17 `runs/01a0db9c-bcc4-70c1-8e3d-4e7157a21ec4/run-result.json` and pinned remediation PostgreSQL 18 `runs/01a0db79-2bb8-75fc-b605-4e176329d80f/run-result.json` reproduce the same detailed failure. All three final runs record only `acknowledgement-deadline` with `knownDefect.status=reproduced` and `blocking=false`.

The isolated Hackage 0.16.1.0 package lane can execute this scenario body with `cabal --project-file=cohort/shibuya-current.project run kenshou-shibuya-test -- --pgmq-live-probe 18` (or `17`). Both runs returned only `acknowledgement-deadline`. Each recorded handler calls 1 and 1, acknowledgement-failure hook calls 0, pre-stop source rows 1 and 1, DLQ rows 0, two active long polls, and post-stop source rows 0 and 0 with DLQ rows 1. This focused probe does not write a sealed CLI run result because the current Shibuya dependency line cannot be linked with the full historical Keiro cohort.

The owner capability `mori://shinzui/shibuya-pgmq-adapter/okf/capabilities/concepts/CAP-1` promises the four acknowledgement decisions and long polling. The scenario classifies only `acknowledgement-deadline` as the known failure on adapter versions below 0.16.2.0; handler count, source conservation, DLQ copy count, and shutdown failures remain blocking. Two occupied long polls suggest a pool scheduling problem, but the probe does not establish its precise cause. A sealed current-release CLI run, a verified safe pool configuration, and an owner regression check remain open.
