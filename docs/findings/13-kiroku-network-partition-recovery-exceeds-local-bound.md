# Kiroku subscription recovery exceeds the local blackhole bound

Status: reproduced against released `kiroku-store` 0.8.0.1 on PostgreSQL 17 and 18. The 60-second deadline is a Kenshou operational target, not a published Kiroku guarantee. The delay is an implementation finding; the desired faster retry is tracked by `mori://shinzui/kiroku/okf/improvement-requests/concepts/IR-16`.

Run `01a0d740-6724-7713-8cba-84b6648d97c8` used the Hackage `kiroku-store` 0.8.0.1 source with SHA-256 `c56c8fa889e07fe7f075c3233976695699e406b185020b8b86f93de3969d6373`, PostgreSQL 18.6 with `fsync=on`, seed `7245215569709266`, `kiroku.conn.keepalives=true`, pool size 10, no statement timeout, and tracing and metrics off. Reproduce with:

```bash
cabal run -v0 kenshou -- run kiroku/subscription/concurrency/network-partition --out runs --dim pg.version=18
```

The proxy reset eighteen sockets, blackholed traffic for twenty seconds, restored forwarding, and reset six more sockets. At the 60-second recovery check, the category subscriber had all 300 distinct positions, while the native `$all` and one-member consumer group had only their 100 baseline positions. The native `$all` path resumed delivery about 91 seconds after forwarding returned; the group resumed at the same time. All three paths eventually covered positions 1–320, and their durable checkpoints reached 320. This earlier result was blocking because the 60-second target was incorrectly classified as a contract. Category delivery replayed 100 earlier positions, a separate implementation finding addressed by `mori://shinzui/kiroku/plans/82-repair-live-reconnect-and-validate-subscription-identity-and-batch-size`. The published at-least-once contract allows reconnect replay and states no batch-sized replay bound.

The original sealed result, verdicts, and per-subscriber delivery timestamps are under `runs/01a0d740-6724-7713-8cba-84b6648d97c8/`. PostgreSQL 17.11 run `01a0d743-6b2e-75df-a22d-a1c254fbffb0` and the prior PostgreSQL 18 run `01a0cc70-a62b-7531-954a-b1967d4193a5` showed the same 100/300/100 split at the deadline and eventual coverage. Diagnostic PostgreSQL 18 run `01a0d746-a273-7019-92b6-0f84e8d27c22` captured publisher pool errors after forwarding resumed, with the native `$all` path delivering position 101 about 91 seconds later. The released publisher retries after a pool error on its next notifier wake or 30-second safety poll. This diagnosis motivated IR-16.

Revision-3 reruns `01a0d74d-7394-7615-ae97-b12757f4acdf` (PostgreSQL 18) and `01a0d74d-7394-7082-9a27-290c2a4035a4` (PostgreSQL 17) each sealed with `blocking: false` and the 60-second miss under `summaries.verdicts.network-partition.implementationFindings`. Final revision-4 runs `01a0d752-4ed9-72d0-bb88-c9b71e1e29ee` (PostgreSQL 18) and `01a0d752-4ed9-7794-acf9-f1079387d17c` (PostgreSQL 17) both sealed `outcome: passed`, `blocking: false`, no contract failures, and two implementation findings: `keepalive-recovery-within-sixty-seconds` and `category-order-after-reconnect`. Each measured 100/300/100 distinct positions at the local deadline and final delivery counts 320/420/320, with complete coverage and checkpoints at 320.

`mori://shinzui/kiroku/okf/capabilities/concepts/CAP-11` and `mori://shinzui/kiroku/okf/capabilities/concepts/CAP-12` promise at-least-once delivery and recovery from transient live database errors. The owner guide at `mori://shinzui/kiroku` project-relative path `docs/user/subscriptions.md` describes a 30-second safety poll for missed notifications and says handlers must tolerate reconnect replay; its artifact-level URI is pending. Neither states a 60-second response deadline for a blackholed database call. The eventual complete delivery supports the published claim. No Kiroku bug report is warranted by these observations.
